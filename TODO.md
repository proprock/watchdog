## Checkout fingerprint follow-ups

- [ ] **WD-135 - Make the checkout fingerprint bounds visible and configurable.** WD-121 returns unknown, and records no snapshot, when a checkout exceeds a bound; nothing tells the user, so the `diff_oscillation` signal silently switches off for that checkout. The bounds are also module constants in `analysis.py` (`CHECKOUT_DEADLINE_SECONDS` 1.5 s, `MAX_DIFF_BYTES` 16 MiB, `MAX_UNTRACKED_FILES` 500, `MAX_UNTRACKED_BYTES` 16 MiB).
  - **Log.** When `git_diff_fingerprint` gives up, `daemon._capture_diff_snapshot` logs one `WARNING` per checkout and reason (`git_failed`, `deadline`, `diff_too_large`, `too_many_untracked`, `untracked_too_large`, `untracked_unreadable`), and again only after the state has fit the bounds. It reuses the existing diagnostics contract: `error_type` always, path detail only under `log_detail`. This needs `git_diff_fingerprint` to report the reason, not just `None`.
  - **Configure.** Decide whether the four bounds become `Limits` fields with the current values as defaults (named like `checkout_fingerprint_max_untracked_files`, validated positive, listed in `config.example.toml` and [docs/storage.md](docs/storage.md#checkout-fingerprint-coverage-wd-121)), or stay constants once the log shows how often they trigger. Prefer the log first: add the fields only if real checkouts hit a bound.
  - **Acceptance:**
    - offline tests for each reason, the once-per-episode logging, and no path in the log without `log_detail`;
    - if fields are added, a config test for defaults, validation, and that the daemon passes them through;
    - the unknown rate on the registered live checkouts, measured from the log, recorded in [verification.md](docs/verification.md).

## Privacy model correction

Watchdog observes one user's own coding sessions, whose prompts and outputs have already been sent to the provider, and analyzes them locally without transmitting anything off the machine without the user's sanction. Decisions that rank privacy above local fidelity and usefulness are wrong for this threat model. The decision text is already updated in [docs/architecture.md](docs/architecture.md) ("Local fidelity and redaction"); these tasks bring the implementation in line.
