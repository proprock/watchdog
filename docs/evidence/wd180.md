# WD-180: Provisional Codex profile, deny effect confirmation and demotion

Date: 2026-10-25. Scope: offline mechanism only; no provider run for the provisional
profile and no local instance change.

## Why

Codex desktop moved from app `26.1016.62342` (backend `0.163.0-alpha.11.2`) to
`26.1021.31345` (backend `0.164.0-alpha.11.1`, read from the session metadata) five
days after the WD-153 probes. A manual probe round per release cannot keep up, and the
installed profile string is not checked against the running version. The user
authorized a TENETS.md change so that the low-risk actions can run on an unprobed
pair under monitoring.

## Decisions

- Profile `windows-desktop-26.1021.31345-0.164.0-alpha.11.1` is **provisional**: the
  cells of the probed desktop profile restricted to `context`, `deny` and `block`.
  `rewrite` and `permit` change or approve a call and stay on exact, probed profiles.
  A failed `deny`, `block` or `context` leaves the harness as if Watchdog were absent.
- Effect confirmation covers `deny` only (`PreToolUse` and `PermissionRequest`). For a
  delivered Codex `deny`, `control_findings` sets `provider_effect` to `contradicted`
  when the same `tool_use_id` finishes after the denial, `blocked` when later hook
  activity in the same session shows the session moved on without it, and leaves it
  unknown otherwise (no activity, no call identity, another action). A value the daemon
  recorded about itself is never read back. `rules stats` reports
  `provider_effect`, `provider_effect_contradicted` and `provider_effect_unknown`.
- Demotion: the daemon remembers delivered denials under a provisional profile
  (bounded, in memory). When ingestion commits a `tool.finish` for a remembered call,
  the profile is written to `profile-demotions.json` and every later decision on it is
  a `log` with gap `profile_demoted`. The record survives a restart and an unreadable
  record counts as demoted (unknown is not zero). The probed profile is never demoted.
  Deleting the record re-enables the profile and belongs after a confirming probe.
  A finish whose `tool_response` only carries the daemon's own refusal text is a
  harness echo, not an execution, and does not demote. When the response is not
  visible (content capture off) the finish counts as a contradiction. The
  record is local daemon state beside the configuration and approved-rule digests;
  anyone able to edit it can already switch every control off, so it is not signed.
  Demotion is deliberately global to the profile (a property of the harness version,
  not of a project) and ends only by deleting the record.
- The native adapter renders the provisional profile for exactly those cells.
- `permit` stays manual: a manual approval and an automatic one are not
  distinguishable from the events.

## Verification

- `tests/test_provisional_profile.py`: cell subset, delivery per cell, rewrite/permit
  log-only, demotion (including restart, damaged record, other profiles unaffected),
  daemon round trip from a delivered deny to a spooled `PostToolUse`, effect states.
- `tests/test_rust_adapter.py`: native rendering rows and daemon round trips for the
  provisional profile; silence for `rewrite` and `permit`.

## Not done

- Only one provisional cell has a live result (see below). The WD-151 desktop run stays
  open; an earlier `bash-deny` attempt on `26.1021.31345` was `inconclusive` because it
  ran under the older profile string (the tool refuses a version mismatch).
- Detection of version drift is separate work: WD-178. The scripted canary is WD-179.
- Effect confirmation for `block`, `context` and `permit` is not attempted.

## Live result (2026-10-25)

`PreToolUse`/`Bash` deny through the production adapter on the provisional profile:
app `26.1021.31345`, backend `0.164.0-alpha.11.1` (read from the session file), one
delivered `deny` control linked to the callback, no side effect. Verdict **supported**
for that one cell ([record](wd151-desktop-provisional-bash-deny.json)).

The negative case on the same pair, same rule and hook without a profile flag: the
command ran (the sentinel exists, no output), one callback was spooled and no control was
delivered. Verdict **supported**, so a missing profile stays silent
([record](wd151-desktop-provisional-no-profile.json)).

`PermissionRequest`/`Bash` deny on the same pair, with an escalation requested: one
`PermissionRequest` callback, one delivered `deny` control, no side effect; the desktop
reported the command as rejected with the rule's message and showed no approval dialog.
Verdict **supported** ([record](wd151-desktop-provisional-permission-deny.json)).

Not yet run: the other provisional cells (`apply_patch` deny, `PostToolUse` and `Stop`
block, `SessionStart` context); they stay unconfirmed and monitored. `permit` and
`rewrite` have no live production-adapter run on any desktop pair.
