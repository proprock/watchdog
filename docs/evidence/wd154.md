# WD-154 - Hook decision-channel latency

Measured on 2026-10-20, Windows 11 10.0.22621 and Python 3.12.13.
All measurements invoke the native adapter directly against scratch state. No
provider or model was invoked, and no installed hook configuration was changed.

## Method

Each run uses `scripts/benchmark_hooks.py --shell direct --samples 20
--idle-seconds 3 --cpu-seconds 3 --max-host-cpu 15 --settle-timeout 45` with
an explicit native adapter. The daemon is ready before the first invocation.
The first process invocation, 16 untimed warmup calls, 20 sequential calls and
20 calls using four workers are distinct. Reported percentiles use nearest rank.
The WD-027 provider, launch mode and sample count are matched; its old report
had 41 events without the current harness's 16 extra untimed warmup calls.
All raw warm samples, CPU windows, delivery/loss counts and restart checks are
retained in the individual JSON files linked by the summary.

The host must average at most 15% CPU over a three-second window before the
first, sequential and concurrent phases, and before the additional socket
phase. CPU during the native phases is recorded separately and includes the
benchmark, daemon and host process-launch work. This is a quiet-window gate,
not a claim that the host is unloaded throughout the four-caller burst.
The first invocation is process-cold, not a controlled cold OS disk cache;
neither executable pages nor filesystem caches are forcibly evicted.

The historical no-channel adapter is rebuilt from `9ea22f7`, the WD-140
comparator. Its schema-1 spool needs the daemon from that same revision:
the current daemon intentionally no longer drains that format. Both binaries
are placed in the same directory; the run order is base/current, current/base,
base/current. This comparison includes all intervening native and daemon
changes and must not attribute their entire difference to discovery reading.
The initial incompatible-daemon attempt failed its delivery check and produced
no accepted report. A preliminary current-adapter run overlapping test execution
was also discarded before the recorded series.

For the controlled source comparison, export the current `native/Cargo.toml`,
`Cargo.lock`, `src/main.rs` and `src/disk.rs` into a scratch directory. Replace
the single expression `PolicySocket::read(&paths.data),` in `main.rs` with
`None::<PolicySocket>,`, then build with `cargo build --release --locked
--manifest-path <scratch>/Cargo.toml`. This deliberately disabled experimental
binary is used only for unsubscribed measurements with the current daemon;
it is never installed. Release optimization may remove unreachable channel
code, so this comparison includes code-size effects as well as the discovery
read. It is not a microbenchmark of the filesystem operation alone.

## Subscribed cells

Use `--provider claude --event PreToolUse --tool Agent --subscribe` for Claude,
and `--provider codex --event PreToolUse --tool apply_patch --subscribe
--codex-control-profile windows-cli-exec-0.162.0-alpha.17.2` for Codex.
`--subscribe` approves a synthetic, never-matching context rule in the scratch
home, requires every native call to reach the decision server and then measures
20 sequential and 20 four-worker socket requests. The no-match response must
be valid `allow`; EOF-framed, empty, malformed, oversized and unexpected-action
responses have focused offline tests. No action is selected in the measured
calls. Existing production-adapter tests cover actual action rendering.

Native whole-process latency includes launch, discovery, the decision exchange
and spooling. The additional socket phase uses a Python client, including
connect/send/read, against the same daemon and the published 300 ms deadline;
it excludes process startup, discovery and spooling. It does not instrument or
establish the exact native-client round-trip duration. The native whole-call
figures provide a separate upper bound in these samples.

Codex's modeled cell is Windows **CLI / exec / 0.162.0-alpha.17.2**, with the
exact installation profile from [WD-151](wd151.md). That evidence confirms
production-adapter denial of `apply_patch`; the benchmark exercises the
subscribed no-match path of that cell. The current installed provider version
is immaterial to a provider-free run. This is not a Codex desktop measurement,
a provider-runner measurement, or fresh live-provider support evidence.
Claude's `Agent` cell has production-adapter evidence on CLI 2.1.292 and
desktop 2.1.299 in [WD-156](wd156.md); these direct timings do not include
either provider runner.

## Results and decisions

[Summary, source revisions, binary hashes and all raw report links](wd154-bench.json).
All 18 accepted runs delivered their expected 57 events, **1,026 total**, with
zero loss counters and preserved state after restart. All four subscribed runs
recorded **57/57 native decision requests**, plus 40 validated Python-client
responses per run. Every pre-phase CPU window was at or below the 15% gate.

Ranges below are per-run percentile ranges, not pooled percentiles, in ms.

| Direct native cell | Sequential p50 | Sequential p95 | Four-caller p95 |
|---|---:|---:|---:|
| Historical WD-027 Codex `Stop` | 29.4 | 35.6 | 65.2 |
| Same-host pre-channel baseline, Codex `Stop` (3 runs) | 38.9-42.6 | 42.9-56.2 | 73.4-94.4 |
| Current Codex `Stop`, alternating with baseline (3 runs) | 39.2-42.0 | 40.6-51.2 | 73.7-102.4 |
| Current Claude `Stop` (2 runs) | 38.0-43.4 | 43.0-45.2 | 87.2-104.8 |
| Subscribed Claude `PreToolUse` / `Agent` (2 runs) | 42.0-44.8 | 44.8-48.6 | 80.0-96.6 |
| Subscribed Codex `PreToolUse` / `apply_patch` (2 runs) | 42.5-42.7 | 44.1-45.2 | 86.0-99.2 |

The same-host **unmodified pre-channel adapter also fails to reproduce WD-027's
29.4 ms p50**. Current warm p50 is inside that comparator's range, and p95
ranges overlap. The historical absolute difference is therefore not evidence
of a new decision-channel warm-path regression. This does not establish which
host/compiler/OS factor changed since WD-027, nor prove zero added cost.

| Python socket client, published budget 300 ms | Sequential p95 | Four-caller p95 | Largest individual sample |
|---|---:|---:|---:|
| Claude `PreToolUse` / `Agent` | 16.2-26.1 | 12.4-21.9 | 26.7 |
| Codex `PreToolUse` / `apply_patch` | 15.8-17.8 | 2.9-5.4 | 19.6 |

**Retain the shared installed entry and fixed 2 s timeout.** Subscribed native
p95 remains below both the 250 ms observation target and 500 ms control budget;
the separate socket samples are comfortably inside the published 300 ms
deadline. There is no measured reason to add the formerly proposed separate
entry with a timeout up to 10 s. This closes that proposal rather than deferring
it to another task. A slow/failed decision still fails open. Provider shell
startup and real provider-runner overhead remain separate WD-026 evidence.

### Cold first invocation and discovery decision

In the legacy/current pairs the first calls were **47.2-64.0 ms** for the
pre-channel adapter and **73.9-114.2 ms** for current. The difference is real
in that series, but those revisions differ in spool format and other native
behavior; it is not an isolated price for reading `socket.json`.

| Same-current-source comparison | First process invocation | Sequential p95 | Four-caller p95 |
|---|---:|---:|---:|
| Normal discovery/channel build | 53.0-62.9 | 40.1-41.9 | 84.3-111.6 |
| Experimental disabled-discovery build | 46.7-110.4 | 40.4-49.9 | 83.6-93.2 |

Normal minus disabled first-call differences, in the three alternating pairs,
were **-35.8, -57.4 and +12.7 ms**. Both artifacts use the current daemon and
raw spool. The normal binary is 490,496 bytes, the disabled variant 436,736;
the historical baseline is 452,608 bytes. These results do **not reproduce a
stable 5-8 ms discovery/channel cold penalty**, and disabling discovery is not
consistently faster. Keep all pairs, including the slow first invocations;
there is no outlier removal or claim of a controlled disk-cache/OS-launch
experiment. Binary size, process/cache state and host effects are not separable
from this small process-cold sample.

**Retain the bounded discovery read; add neither a cache nor a skip.** An
adapter process handles one hook, so an in-process cache saves no later hook
invocation. A cross-process subscription cache or provider/event skip would
need an invalidation contract and could miss newly enabled subscriptions. The
measurements do not demonstrate a benefit justifying that added state or a
change to discovery freshness. The cold cost is disclosed rather than called
zero; future optimization should start with a reproducible matched-source
regression, not the historical absolute WD-027 number.
