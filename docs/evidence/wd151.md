# WD-151: Codex CLI control profiles

Status (2026-10-15): CLI implementation verified offline, with production-adapter
live evidence for `PreToolUse`/`apply_patch` deny on Windows Codex CLI
0.162.0-alpha.17.2. Codex desktop remains gated by WD-153. Other cells retain
their original provider-probe scope and the offline adapter evidence below;
the single production live case does not establish effects for every cell.

## Probe basis and runtime gate

The exact CLI cells below come from the sanitized, corrected WD-163 records and
retain their observed Windows version and mode. `--codex-control-profile VALUE`
selects one installation-scoped profile for the native hook command. It is
Windows-only. The operator must confirm the exact executable version and mode.
There is no greater-version inheritance; payload `surface` and `provider_version`
are descriptive only and cannot enable a profile. Missing, default, and unknown
profiles remain silent. The CLI-only flag must not be added to shared CLI-and-
desktop hook commands.

| Profile | Confirmed cells |
|---|---|
| `windows-cli-0.160.0` | `SessionStart`/context; `UserPromptSubmit`/context; `PostToolUse`/`Bash`/context; `PreToolUse`/`Bash`/deny or rewrite; `SubagentStop`/block |
| `windows-cli-exec-0.162.0-alpha.17.2` | `PreToolUse`/`Bash`/context; `PreToolUse`/`apply_patch`/deny or context; `SubagentStart`/context; `Stop`/block |
| `windows-cli-interactive-0.162.0-alpha.17.2` | `PreToolUse`/`apply_patch`/rewrite only, evidenced by an operator-approved scratch edit |

Historical `PermissionRequest` and named MCP fixture observations are not enabled.
Apply-patch rewrite requires a string `updatedInput.command`; the native response
does not set `permissionDecision: allow`. Unknown or unsupported matched requests
are fail-open and may produce only a bounded, log-only `capability_gap` with
reason `unsupported_codex_cell`, `requested_action`, and `delivered_at: null`.
Deduplicate for ten minutes per rule/version/profile/project without consuming
the control throttle. Non-null `delivered_at` means the daemon sent its socket
response; it does not establish adapter rendering or provider effect.

## Production-adapter live evidence

The [corrected production run](wd151-codex-cli-production-attempt-2.json) used
Windows Codex CLI 0.162.0-alpha.17.2 with `gpt-6.1-sol`, low effort, and the exact
`windows-cli-exec-0.162.0-alpha.17.2` installation profile. One `PreToolUse`
callback carried `tool_name = apply_patch` and string `tool_input.command`.
The real 0.1.5 native adapter rendered deny, the provider's denial reason and
absence of the patch effect were checked, and one approved deny envelope was
read back from the scratch Store with non-null `delivered_at` and an evidence ID
matching the native-spooled callback. Two observation events were spooled.
The provider exited zero without timeout; owned-process, profile, and scratch
cleanup were confirmed.

The daemon decision server was the production `_policy_server` implementation
running in-process under the scratch daemon lock. After handler completion,
the runner used `_drain_spool` and `Inbox.drain` to persist and read the events.
This verifies production adapter, decision channel, provider effect, and store
delivery; it does not measure the detached daemon's periodic ingestion cadence
or lifecycle. The observed tool path was `exec`; this evidence covers the named
`apply_patch` hook cell and does not generalize to other wrapped tools.

The [first attempt](wd151-codex-cli-production.json) was inconclusive: two patch
callbacks, three spooled events, no rendered deny, and no persisted control.
Its temporary project was registered as a directory before `git init`; the
subsequent Git checkout could not resolve to that registration. The runner now
initializes Git before registration. A failing-then-passing ordering regression
and a native-to-store test using a Git checkout cover this setup defect. Both
live attempts confirmed cleanup; the first attempt is not provider acceptance.

Reproduce the single supported production-probe workload with a new output file:

```powershell
uv run python scripts/codex_control_probe.py --live --case pre-tool-apply-patch-deny --codex PATH --production-adapter ABSOLUTE_ADAPTER_PATH --output NEW.json
```

The runner requires the exact CLI version and native decision schema 2 before
dispatch. It creates a separate Codex home, Git project, approved rule, and
Watchdog config/data/runtime; active provider configuration is not modified.
