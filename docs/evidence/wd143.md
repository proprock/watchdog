# WD-143: approved Python execution and offline replay

Date: 2026-10-18. Implements the accepted [execution decision](../architecture.md#wd-143-python-rule-execution-decision-2026-10-18)
and [design review](wd143-review.md). This record concerns offline implementation
verification, not live provider acceptance or approval of a real rule.

## Execution contract

- `rules/api.py` exposes the `Rule` protocol, `Event` mapping, read-only `Context`
  snapshots and `Decision`. Python inputs recursively freeze event/configuration
  collections; session state is immutable.
- `rules/registry.py` discovers `.toml` and `.py` files within the existing file
  and byte limits. Python metadata is a literal `RULE` dictionary; discovery
  checks syntax and validates metadata without module initialization. Duplicate
  names across formats and built-in shadows are invalid. Python signatures
  include the byte hash even when size and modification time are unchanged.
- `rules/python.py::PythonHost.evaluate` checks the approved SHA-256 and compiles
  that same in-memory snapshot. It never obtains executable code by reopening a
  pathname. The worker initializes a fresh module and invokes `evaluate(ctx)`
  under one supervisor waiting budget.
- Four worker slots per daemon configuration, one in-flight evaluation per rule,
  no pending queue. A timed-out thread keeps its slot while alive. Late decisions
  are discarded and the rule name remains disabled until daemon restart, even
  after byte changes or the thread's eventual exit. Exceptions and invalid
  results fail open and mark the rule degraded. Timeout diagnostics are logged
  independently of earlier rule exceptions.
- The host validates returned actions and supplies rule attribution. Engine
  integration retains expiry, throttling, stop-loop protection, exact Codex
  profile/capability gates and action recording. Both kill switches are checked
  before Python initialization.
- Approval alone leaves Python inactive; enablement is a separate command.
  `rules test NAME --session ID` permits an approved, disabled rule, verifies
  current approval before initialization, and reads recorded stores without
  writing or invoking the live decision channel. It rejects ambiguous session
  IDs across projects/providers and reconstructs state before each event.

Replay reports hypothetical rule evaluations, not delivery. Cooldowns, per-turn
caps and daemon kill/capability gates are outside its simulation, as the JSON
`scope` states. Model proposals and candidate classification remain WD-144.

## Verification

- Focused Python execution/engine and replay tests: 24 passed.
- Existing registry, built-in and CLI checks: 181 passed at the initial execution
  integration checkpoint. The final full run covers the stable combined diff.
- Ruff, Ruff format, ty and `uv build` passed on the final Python diff.
- The first sandboxed full run recorded 1643 passed, 33 failed and 1 skipped in
  567.25 seconds. Failures were subprocess/daemon waiting timeouts, including the
  invalid CLI-command test. Five representative failures passed outside the
  sandbox (44.40 seconds), retaining their original timeouts and parallel setup.
- The final full run outside the sandbox recorded 1675 passed, 1 failed and
  1 skipped in 159.81 seconds. Its sole failure was the existing PowerShell
  command-shape test's 10-second subprocess timeout. Running that same test
  alone, with unchanged timeout and no parallel load, passed in 6.25 seconds:
  `uv run pytest tests/test_hook_install.py::test_generated_command_executes_with_shell_metacharacters -n 0`.
  This is a full-run timing limitation, not a green combined-suite result.

## Local installation

The existing user-local instance was inspected before deployment: it was alive
but already degraded with `storage_unavailable`, an empty spool and no recorded
decision-channel requests. The verified wheel was force-reinstalled without
dependencies using the local LIVE.md procedure; the stable adapter was replaced,
and that exact instance was stopped and started with its existing arguments.
Post-restart status reported `running`, `alive: true`, no errors, warnings,
degradation reasons or backlog, and storage available. The previous degradation
cleared after restart; no storage repair or configuration change was made.
Eight installed Python files and the adapter were compared with the verified
checkout artifacts and matched byte for byte. No real rule was approved or
enabled and no provider configuration/trust record was changed. This task does
not infer provider effects from daemon status or adapter rendering.

## Operating limits

Approval is the user's responsibility. Threads run trusted code inside the
daemon and provide neither a sandbox nor forced termination or immunity from
shared-state/lock failures. Timeout recovery is diagnosis, code correction,
approval of changed bytes and daemon restart. Tests release their synthetic
blocked threads and never call a provider or modify active provider settings.
