# WD-170: a spool record whose `cwd` is gone killed the daemon on every start

Observed 2026-10-08 on the user-local instance while recording calibration verdicts: a
control request timed out waiting for the daemon's acknowledgement.

## What was wrong

- The newest event in the project store was 2026-10-06 20:58 UTC, about two days earlier.
  The spool held about 2,280 records and the project inbox about 1,455.
- `daemon status` answered `alive: true`, because it reads only the daemon lock, and
  `degraded` with an empty `status.json` (`{}` is what each launch writes first). The log
  held thousands of `lifecycle started` lines and no `stopped`: every hook launched a
  daemon that exited within a second.
- Run in isolation on a copy of the data with the installed interpreter, the daemon failed
  in `_drain_spool` at `registry.resolve(Path(cwd))`: a spool record carried the `cwd` of a
  temporary directory that no longer existed, `discover` raised `RegistryError`, and nothing
  caught it. Files are drained in name (UUID) order, so the first poison record stopped
  every record behind it. All 91 such records came from `watchdog-wd139*` live-probe
  directories deleted after the probes ran; no other missing directory was present.

## Fix

`_drain_spool` catches `RegistryError` around project resolution. A `cwd` that no longer
exists is discarded and logged (`decision=discarded reason=unresolvable_cwd`, no path in
the log). One that still exists, which may be a transient Git timeout, stays for the next
pass and is logged once (`decision=deferred`). The diagnostics vocabulary gained the
`unresolvable_cwd` reason. Tests (`tests/test_daemon.py`): a poison record ahead of a valid
one still lets the valid one through, and a transient failure keeps its record and logs once.
The full suite passed (1229 passed, 1 skipped) before the live deployment.

## Live deployment

1. All five project databases were copied with the SQLite backup API first
   (integrity check ok, schema 7).
2. The wheel was installed into the installed environment and the daemon restarted by
   itself on the next hook. The log shows 91 `unresolvable_cwd` discards, equal to the 91
   poison records counted beforehand, and the pending control requests were acknowledged
   (the previous acknowledgement was 2026-09-14).
3. The five databases upgraded from schema 7 to 8 on that start.
4. The backlog drained in about an hour: 24,167 events in the project store at the start
   and 29,468 when the spool and inbox were empty (live traffic included). Ingestion ran
   at about 50 to 55 events per minute, which is why it took that long; WD-172 tracks it.
5. A later planned restart (stop, wheel 0.1.5, start) left the daemon `running`, not
   paused, and events kept arriving in real time.

## Not covered

- A daemon that dies at startup for another reason is still reported as `alive`;
  WD-173 covers that visibility.
- The discarded probe records were not recoverable events: their directories no longer
  existed, so no project could be attributed.
