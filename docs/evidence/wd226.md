# WD-226: daemon file-read failure provenance

The [WD-223 full run](wd223.md) failed two tests under parallel load. Both
passed in a serial repeat. A fresh run of just the two tests with two pytest
workers passed (2 passed in 6.62 seconds); that smaller workload does not
reproduce the original full-suite conditions.

## Capture store readiness

The transcript test waits for the capture database file to exist and then
opens it read-only. `CaptureStore.connect` creates the SQLite file before
`_initialize` commits its schema and `user_version`. The read-only open checks
the version and rejects version 0, including an uninitialized file. File
existence therefore does not establish that the schema is ready.

In a controlled experiment, a writer thread was paused immediately before
`_initialize` after SQLite opened the new file. The file existed, and a
read-only `CaptureStore.connect` raised `StorageError: Capture store version
0, expected 3`. After releasing the writer and joining it, the read-only open
reported version 3. This reproduces the observed error and establishes the
window; the original run did not record the precise interleaving. Invalid or
incompatible stores must remain distinguishable from an initializing store.

## Windows policy discovery access

The original traceback shows `Path.read_text` raising `PermissionError` while
the test polled for the newly approved subscription. The daemon publishes the
initial discovery document and subscription changes using `atomic_write`,
which writes and synchronizes a sibling temporary file and replaces the
destination. The original traceback did not capture the Windows error code or
the identity of a conflicting handle.

On Windows, a controlled experiment concurrently read a discovery-shaped file
with `Path.read_text` while a writer repeatedly published it with the same
`atomic_write` function. It observed 18,406 successful reads, 145 reader
`PermissionError` exceptions (no `winerror` exposed), and one writer
`PermissionError` with `winerror` 5; the writer stopped at that exception
before its 3,000-iteration limit. The experiment reproduces access failures
under concurrent publication and reading, but does not identify the handle or
prove the precise cause of the historical failure. The capture-store and
discovery failures have separate observed mechanisms.

Production policy readers and publication semantics also matter: the native
adapter treats discovery read failures as unavailable, and readiness handles
read errors. WD-231 tracks selecting and verifying remedies without hiding
permanent schema errors or weakening existing behavioral assertions. No
production or test behavior was changed in this investigation.
