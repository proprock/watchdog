# WD-158 - Quick and full usage statistics, indexed overview reads

## Change

`inspection.usage(..., detailed=True)` preserves the full usage report, including
all six token breakdowns, process statistics, coverage, and optional provider,
model, and day pricing. `detailed=False` returns the same project/window
metadata, provider token totals, and optional provider pricing without those
extra scans. `overview` uses the quick mode. A future WebUI can request either
mode through this shared API; no UI or CLI flag is added here.

The writer installs two additive indexes on new and existing schema-v9 stores:

- `events_provider_session(provider, session_id)`, for non-null sessions.
  Its implicit rowid covers both summary counts and pending findings watermarks.
- `event_facts_usage_identity(provider, session_id, agent_id, native_event_id)`,
  restricted to usage with a native identity. It covers the unwindowed first-copy
  grouping used by token totals and pricing.

There is no disk report cache or new schema version. Read-only commands work on
stores without these indexes, and never install them. Counters, null coverage,
time-window boundaries, first-copy semantics, and prices are unchanged.

## Profile and fixed-data comparison

Windows, Python 3.12.13, 2026-10-20. The host was serving other work, so samples
include scheduling and filesystem noise. SQLite's backup API copied the five
live databases into a temporary directory: 60,816 events total, with 39,494 in
the largest store. All benchmark reads used short read-only snapshots.

An initial `cProfile` of full `usage` on the largest live store took 1.05 s:
seven token groupings used 0.67 s, process statistics 0.26 s, and coverage
0.11 s. The initial snapshot `overview` profile took 2.85 s, including 1.91 s
in full usage across projects, 0.45 s in summary, and 0.45 s in findings.

For the comparison below, the baseline inspection module was loaded from the
branch's initial HEAD without changing the checkout. Three calls per case used
the same copied rows. The optimized reader before index installation produced
exactly the same overview JSON as the baseline. After opening each copy with
the current Store, provider totals remained identical.

| Read | Three samples, seconds |
|---|---|
| Baseline overview, in process | 9.4114, 3.8862, 3.3786 |
| Quick overview, before new indexes | 1.1695, 1.0226, 0.9959 |
| Indexed overview, in process | 0.1723, 0.1899, 0.2076 |
| Baseline full usage, largest store | 1.2785, 1.1036, 1.0737 |
| Indexed full usage, largest store | 0.8998, 0.6692, 0.6809 |
| Indexed quick usage, largest store | 0.0364, 0.0459, 0.0401 |

Opening the existing copied stores to install indexes took 0.332, 0.142, 0.015,
0.033, and 0.017 s. This is current-schema startup, not a repeat of the older
v7-to-v8 migration measured in WD-141.

The remaining CLI cost is explained rather than hidden by an in-process timing:
`cProfile` of a fresh CLI process measured 1.084 s overall, 0.821 s in imports
(including CLI, daemon, storage, and Pydantic initialization), and 0.206 s in
`inspection.overview`. The command lowers its process priority as before.
CLI import restructuring is outside this change; the future persistent UI can
use the in-process read without repeatedly paying Python startup.

## Verification

Regression tests compare overview with full CLI usage, including tariffs,
bounded windows, and duplicate native responses whose first copy is outside
the selected window. A query guard rejects unused dimensions, process scans,
and coverage scans. A direct API contract verifies both detail modes and the
unchanged default. Query-plan tests reopen an existing store missing the new
indexes and check actual token SQL, pending-session SQL, and summary grouping.

The initial query guard and index-plan test failed before implementation.
Focused storage/overview/facts checks passed. The first full run had 1,734 passed,
one skipped, and one failure: the existing v6 migration contract needed the new
index in its exact expected set. After updating that expectation, all 29 focused
overview/v6 migration tests passed.

Final full suite: **1,735 passed, 1 skipped in 129.16 s**. Ruff lint/format,
`uv run ty check`, `uv build`, and diff hygiene passed. The unchanged native
adapter was rebuilt with `cargo build --release --locked` for the local update.
No provider probes, model calls, or remote CI runs were performed by this task.

## Live daemon acceptance

The verified wheel was force-reinstalled without dependencies into the existing
user-local environment using `uv pip`, and the stable native adapter was
replaced from the release build. Configuration/data/runtime arguments came
verbatim from the installed hook. Hook definitions and trust records were not
edited. The owned daemon was stopped and started at those same paths at
08:46 Warsaw time on 2026-10-20; its PID and instance ID changed. The installed
`inspection.py` and `storage.py` hashes match the verified checkout, and both
new indexes are present in all five live stores.

Immediately before the restart, the live stores held 60,938 events and pending
sessions were **1, 0, 0, 0, 0**. After the restart they held 60,946 events and
all five pending counts were **0**, with findings `state="ready"`. The active
project's `as_of` advanced to `2026-10-20T06:47:43.070504+00:00`. Separate
installed-Python CLI `overview` processes completed in **1.1151, 0.9678,
1.0714 s**, each with exit code 0. The median is just over 1 s; the import
profile above explains the residual cost and meets WD-158's alternative
acceptance criterion without claiming every call is below 1 s.

The INFO-level live log contains three `lifecycle`, one `configuration`, and one
`enrichment` event since restart. It contains **zero `event=findings` failures**;
that event is emitted only on refresh failure, not successful refreshes.
Ready findings, the advancing watermark, and pending draining to zero verify
the successful daemon path.

Global daemon health was already `degraded` before deployment and remains so
because one project retains `transcript_unreadable`. A transient
`storage_unavailable` reason seen in the first baseline status was absent before
the restart and after it, so its disappearance is not attributed to this patch.
Backlog is empty. This validates reporting and findings refresh, not a clean
bill of health for that unrelated transcript source.
