# WD-216 verification

The registry saves an alias when a project is registered. Removing another
project or relocating the checkout preserves that alias. The explicit
`project rename` command accepts the current alias or UUID, and rejects a new
alias that would take over another project's alias or UUID.

## Offline checks on 2026-11-12

- The task tests reproduced alias reassignment on removal and relocation,
  missing alias persistence, and the lack of explicit rename. A review case
  reproduced assignment of another project's UUID as an alias before the
  collision check was added.
- The focused registry, CLI, daemon, and scanner run passed 177 tests. The root
  suite passed 2157 tests with one skip and required the native adapter.
- The insights suite passed 263 tests and reported a Starlette test-client
  deprecation warning.
- Ruff lint and format, ty, and `uv build --all-packages` passed.
- On a synthetic configuration with colliding directory names and one saved
  custom alias, the migration preserved all visible aliases and other settings.
  A second invocation left the configuration byte-identical.

## Installed daemon checks on 2026-11-12

Paused the installed daemon, installed the verified Python wheel, and ran
`scripts/pin_project_aliases.py` with the paths from the installed hook. The
script saved the 15 existing aliases. The project UUIDs, visible aliases, and
other configuration values matched the pre-migration snapshot. A second
invocation saved zero aliases and left the file byte-identical.

The restarted daemon reached `running` and `doctor` reported zero warnings.
All 15 registered store manifests matched the persisted aliases. Both hook
definition hashes matched across the update.

The first preflight reported `storage_unavailable` before any installation
step. A fresh status and `doctor` check returned healthy before deployment.
WD-215 tracks the intermittent symptom.
