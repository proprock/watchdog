# WD-173: explain daemon startup failures and ingestion stalls

Implemented 2026-10-16. WD-170 exposed the gap: OS lock ownership could be true
while each short-lived daemon died before publishing a heartbeat, and status
offered no reason for degradation.

## Behavior

- `daemon status` now returns `reasons` and `health` evidence independently of
  `alive`. A start that releases ownership before its first heartbeat reports
  `degraded` / `startup_failed` in one status call, even with `alive: false`.
  Three unmatched starts within 60 seconds add `startup_crash_loop`.
- The daemon owner atomically retains at most 32 pending starts in the data
  directory; a first published heartbeat clears them. This survives runtime
  status resets and does not depend on diagnostic log level or rotation.
  Invalid evidence stays unavailable; diagnostic write failures never interrupt
  collection.
- Queue observations sample at most every ten seconds. A nonempty spool or
  project inbox with no shrink or drain progress across multiple samples for
  60 seconds contributes `backlog_stalled`, with affected queue IDs. Progress
  resets only that queue's clock, including movement at constant occupancy.
- On-demand read-only SQLite comparisons expose newest stored event time,
  newest spool file modification time and their lag. Spool records waiting
  at least 60 seconds while storage trails by at least 60 seconds contribute
  `storage_lag`. Fresh work after idle gets a grace period. Missing databases
  are not created; invalid, busy, over-budget or incomplete comparisons stay
  unavailable. Each database has a 100 ms lock timeout and scan budget.
- An idle daemon with a current heartbeat and empty queues stays `running`.
  Pause still takes precedence; the command neither starts nor kills a daemon.
  Existing decision-channel warning and project/transcript evidence remain.

Spool timestamps are explicitly labeled `filesystem_mtime`, not provider event
timestamps. Queue and storage inspection covers the first 32 registered projects;
a larger registry makes the storage comparison unavailable. The complete reason
vocabulary and expiry rules are in [daemon.md](../daemon.md).

## Verification

New regression tests first failed against the previous implementation. The
focused final serial run passed **129 tests**:

```console
uv run pytest tests/test_daemon_health.py tests/test_daemon_lifecycle.py tests/test_daemon.py -n 0 --basetemp <fresh-user-temp-directory> -q
```

Key acceptance tests in `tests/test_daemon_health.py`:

- `test_startup_death_has_a_reason_in_one_status_call`: real daemon ownership
  and lifecycle setup, injected fatal startup failure, then one status call;
  both one-start and three-start cases.
- `test_idle_daemon_with_empty_queues_stays_running`: actual poll loop publishes
  a healthy heartbeat, status stays running, then cooperative pause.
- `test_poll_publishes_stall_evidence_without_repeated_status_calls`: two poll
  observations spanning the window, then one status call names the stall.
- `test_status_detects_storage_lag_but_allows_new_traffic_after_idle`: real
  temporary SQLite store and spool, with controlled timestamps.
- Independent spool/inbox progress, unavailable stores, malformed backlog
  evidence, and missing/stale/invalid heartbeat cases are also covered.

`tests/test_daemon_lifecycle.py` covers durable persistence, expiry, bounded
history and reads, readiness recovery, corruption, nonfinite timestamps and
best-effort writes. Tests use synthetic data and temporary directories, with
no provider calls or active hook-configuration changes.

The first parallel affected-module run had seven detached-daemon startup
timeouts; 95 tests passed. An isolated failed lifecycle test and the complete
129-test serial affected set then passed without a code change to startup.
The final full suite passed with its default parallel configuration:
**1466 passed, 1 skipped in 98.06 seconds**, exit 0. Ruff lint and formatting,
`uv run ty check`, `uv build`, and diff hygiene passed. The unchanged native
adapter's release build also succeeded; no CI or live provider run is claimed.

## Local deployment

The verified wheel and unchanged native adapter were installed into the existing
user-local instance using `LIVE.md`. Config/data/runtime arguments were copied
verbatim from the installed Codex hook command. The old daemon was stopped
cooperatively, then a different instance was started; hook definitions and trust
records were not changed.

The new instance's first status reported zero unmatched starts, no stalled queues
and 1.39 seconds of spool-to-store timestamp lag. A later status on the same
instance had an advancing heartbeat and newest stored event timestamp; the spool
and all five project inboxes were empty. Storage inspection was available.

Both before and after the update the overall state was `degraded`. The new status
explains it as `project_or_configuration_error`, with an existing project's active
`transcript_unreadable` code in `transcript_failures`. This is separate from startup
or ingestion health; the deployment does not claim that transcript coverage is
healthy or repair unrelated transcript references.
