# WD-222 verification

## Finding and decision

All 28 reported dimension/session differences across the 12 affected Codex main
streams are explained by captured source records and historical import coverage.
No current collector or parser defect was verified. No production accounting,
raw records, historical receipts, installed database, or provider configuration
was changed.

Watchdog uses fieldwise deltas of `token_usage_record.thread_token_usage`, as
specified in `docs/architecture.md`. Insights sums `event_msg.token_count`'s
`last_token_usage`, reconciling repeated cumulative notifications within their
recorded turn/generation coordinates. `insights/docs/context-efficiency-audit.md`
documents those coordinates; `insights/README.md` says doctor compares the two
conventions without correcting either one.

The captured notifications omit costs present in 18 native compaction responses
across 11 streams. This is an observed source-coverage limitation, not an assertion
that excluding compaction costs was an explicit product decision. One of those
streams also repeats the same cumulative totals and last-usage tuple under a new
turn ID. Insights merges the two observations in the original turn but counts
the new turn separately, as its documented identity convention requires.

The remaining stream had imported 601 of the 669 retained records. Parsing its
601-record prefix exactly reproduces the snapshot; parsing all 669 records
matches Watchdog. This verifies historical projection lag, not a parser loss.

Replacing Insights accounting with native usage would change its convention;
the investigation provides no justification for silently doing so merely to
eliminate doctor differences. Codex subagent accounting remains WD-223.

## Source verification and replay, November 13, 2026

The original WD-195 snapshot was opened read-only. Repeating reconciliation
exactly matched all 204 saved Codex main dimension rows: 51 sessions times four
dimensions, including unavailable cache-write comparisons.

The 12 affected main streams contain 19,847 retained records and 2,689 distinct
native response IDs. Every historical native ID occurs in the captured source,
and there are no additional native IDs there. For every stream, the snapshot's
record cursor and byte count match a captured prefix, and parsing that prefix
exactly matches its three known historical Insights totals. Eleven prefixes
already cover their entire retained streams; the twelfth stops at record 601.

All 12 retained streams were replayed through the current collector into fresh,
temporary stores, draining bounded read windows to EOF and paginating events.
Each native response produced exactly one usage event; deltas matched the
historical Watchdog totals in all three compared dimensions. Draining reached EOF
without duplicate usage. The replay recorded only the existing
`tool_version_unsupported` diagnostic for these streams' tool grammar; no usage
failure or counter-reset gap occurred. This does not qualify tool/control support.
Temporary stores were removed. Source stores and the snapshot remained read-only;
no model or live provider probe was invoked.

Compaction identity was verified using `compacted.compaction_response_id` against
the native response IDs. After removing those responses, the multiset of native
usage tuples is fully covered by parsed notifications. The only nonzero extra
notification is `(100366, 98304, 1734)` for input, cached input, and output. Its
cumulative total is identical across two distinct recorded turns in the same
generation; the original turn contains two notifications that correctly merge.
Zero-valued extra notifications add no tokens.

- Native compaction usage contributes to collector deltas without inventing a
  missing notification; the parser retains unknown cache creation and source bytes.
