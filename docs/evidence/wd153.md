## Evidence boundaries

- `scripts/codex_desktop_probe.py` prepares one case per fresh scratch Git
  repository, outside registered Watchdog projects. It writes only project-local
  `.codex/hooks.json`; the operator reviews native trust, starts a fresh desktop
  chat, and supplies the app version from About. The backend version comes from
  the same session's rollout metadata, independently of the installed CLI.
- `scripts/claude_manual_probe.py` prepares one interactive Claude case at a time,
  including ordinary permission baseline, `PreToolUse` ask, `PermissionRequest`
  allow/deny, and Notification observations. The operator drives the real CLI
  and its permission dialog. Headless refusal does not establish interactive ask.
- Each collector uses callback/session/transcript evidence and emits sanitized
  `watchdog.probe-result.v1` records. Raw paths, prompts, hook input and output
  remain in scratch. Missing callbacks, unknown version, mismatched sessions, or
  unfinished provider work cannot establish a supported capability.
- The direct provider probes do not invoke the production Watchdog adapter or
  measure daemon/store delivery. Those stages cannot be claimed from model
  output. Retained scratch/chat state is recorded, with overall cleanup still
  incomplete until separately confirmed.
- Global hooks may still run alongside project-local hooks. Neither kit edits
  global provider settings, creates a runtime control profile, bypasses native
  trust, or launches a provider from pytest.

The reviewed [Codex hook contract](https://learn.chatgpt.com/docs/hooks) describes
project-local discovery, native review/trust, and per-event output shapes. The
[Claude Notification contract](https://code.claude.com/docs/en/hooks#notification)
states that notifications cannot be blocked or modified. Documentation is a
probe-design reference; it does not replace live evidence for a surface/version.

## Operator sequence

Use a new scratch directory and evidence filename for every case or retry.
Pass `--config` when the active Watchdog configuration differs from the default.
The kits refuse scratch locations inside registered projects. Review the printed
steps before opening the provider. Do not add CLI control profiles to shared
Codex desktop hook commands.

Independent cases may be run in a small operator batch. Each case still needs
its own scratch folder, trusted hook, fresh chat and single prompt. Collect each
case separately after terminal completion; keep its scratch folder available
until collection has saved the record and disabled the owned hook.

```powershell
$scratch = Join-Path $env:TEMP 'watchdog-wd153-codex-session-start-attempt-1'
uv run python scripts/codex_desktop_probe.py prepare --root $scratch --case session-start-context
```

Open that folder in Codex desktop, review and trust the exact project hook,
then start a fresh chat. Send the printed prompt once, wait for completion, and
record the exact app version from About. If native hook review or a requested
operation is unavailable, record the reason instead of bypassing it. Collection
disables the unchanged owned hook by renaming it; it preserves raw diagnostics
and reports that chat/scratch cleanup has not been confirmed.

```powershell
uv run python scripts/codex_desktop_probe.py collect --root $scratch --desktop-version APP_VERSION --output NEW_RESULT.json
```

Start Claude with the project-local settings in a fresh scratch folder for each
printed case. Keep its ordinary permission mode; do not enable bypass mode or
add permanent approvals. The baseline and ask trials must remain comparable.

```powershell

```

Follow the kit's printed instructions, exit the owned CLI session, then collect

```powershell

```
