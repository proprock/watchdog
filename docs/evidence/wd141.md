# WD-141 - Incremental session state and materialized findings

## Delivered

- `state.py`: `SessionState` (frozen) and the pure `apply(state, envelope)`. It keeps counters,
  timestamps, the coordinator model, and the last 16 tool-call signatures as SHA-256 hashes of the
  tool input and output plus the outcome. No prompt, command, or output text; the hashes are null
  when `capture_content` is off. `fold` replays a sequence and is shared by the migration and tests.
- Schema v8 (`storage.py`): `session_state`, `session_findings`, and `session_analysis` (the
  report's `gaps` and the staleness watermark; this third table is not in the original design).
  `Store.put` applies the state in the event's own transaction, so a duplicate is never counted twice.
  `Store.refresh_session_findings` re-analyzes one session. Opening a v7 store replays every event
  and analyzes every session after a free-space check. Retention and `purge` drop the rows of
  sessions whose events are gone.
- Daemon (`_SessionTracker`): states in memory for the decision channel, restored from the table
  after a restart; a session is refreshed at most once a minute, at once after `session.end`, with a
  200 ms budget per tick (at least one session, longest-waiting first). A failure is logged once per
  episode (`event="findings"`, `decision="unavailable"`) and never degrades the project.
- `rules.api.Context` carries the calling agent's state to rules as `Context.session`; the
  `subagent_same_model` rule is unchanged and still reads the database (WD-142 moves it).
- `overview` reads `session_findings` and adds `findings.as_of` and `findings.pending_sessions`;
  a store older than v8 reports `findings` as `unsupported`. `report` is unchanged.
- `scripts/benchmark_overview.py` builds the synthetic store and times it.

## Decisions

- **Per-session findings in `overview`.** `report` analyzes a project's events together, so a
  signature repeated across sessions adds up. `overview` now sums per-session analyses, the way
  `insights sessions` already analyzes sessions. One `diff_oscillation` shared by several sessions of
  a checkout has one fingerprint and counts once. `by_rule` still counts findings, not the sum of
  their `count` that the original text proposed, so the number keeps its meaning.
- **No command text in state.** The original design kept the last 32 commands. A hash only detects an
  identical command, which `last_signatures` already does, and raw commands would carry secrets
  into a table that outlives content retention. A predicate that needs "was a test run since the last
  edit" gets a derived flag in `apply` (WD-142), not the string.
- **`edits_since_last_call`** counts edit-class calls (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`,
  Codex `apply_patch`) finished since the last other call finished, and resets when another call
  finishes. The original text said an `Edit` resets it; the counter reads as "edits since the last
  call", so this follows the name.
- **Replay in the migration**, not lazily: the store is consistent the moment it opens.

## Measurements

Windows 11 host, Python 3.12.13, noisy (other work ran between runs).

**Synthetic, 15000 events, 300 sessions** ([wd141-overview-bench.json](wd141-overview-bench.json)):
`overview` 0.14-0.16 s over three runs; the two per-provider `report` passes `overview` used to run
0.64-0.79 s. Refreshing all 300 sessions took 1.2-6.4 s, bound by one fsync per session.

**Write path, 2000 events, with and without the state upsert:** 10.9 s and 9.9 s without, 10.3 s and
10.5 s with; the commit dominates (about 155-200 events/s).

**Read-only copy of the live stores** (SQLite backup into a scratch directory; 45457 events in five
projects, three of them small):

| Measure | Result |
|---|---|
| Per-provider `report` passes (the old findings cost) | 6.0, 7.4, 7.5 s |
| `overview` after the upgrade | 1.4-1.9 s (2.3-2.9 s during one noisy run) |
| of which findings / `usage` / `summary` | 0.32-0.35 / 1.0-1.14 / 0.32-0.36 s |
| v7 to v8 upgrade, large stores (24167 and 18288 events) | 8.4 s and 5.2 s (38 s and 17 s before the snapshot cache) |
| v7 to v8 upgrade, the other three | 1.1 s, 0.06 s, 0.07 s |
| Pending sessions after the upgrade | 0 in every project |

Finding counts per rule on the two large projects, as codex / claude: the project-wide `report`
before, the per-session sum in `overview` after. The small projects agree or have no findings.

| Rule | Project 1 before | Project 1 after | Project 2 before | Project 2 after |
|---|---|---|---|---|
| `diff_oscillation` | 26 / 19 | 26 / 19 | 18 / 18 | 18 / 18 |
| `same_model_subagent_spawn` | none / 19 | none / 19 | none / 2 | none / 2 |
| `repeated_tool_outcome` | 51 / 46 | 25 / 12 | 48 / 3 | 41 / 1 |

The drop is the cross-session repeats described above; no rule or threshold was tuned to it.
