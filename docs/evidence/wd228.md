# WD-228: native spool publication under contention

[WD-224](wd224.md) measured native publishers holding the shared admission lock
for up to 449 ms. The largest measured hold included 277 ms in `sync_all`,
127 ms in temporary creation and write, and 42 ms in file close.

The adapter now reserves one file and its full serialized byte length under
`admission.lock`. It closes the sizing handle before unlocking so that a
Windows directory scan sees the reserved length. Native and Python publishers
already account for regular `.tmp` files. The adapter reopens without
truncating, writes and syncs outside the lock, and takes the lock again for the
atomic rename. Serializing rename with quota scans prevents a scan from missing
a file in transition. The two acquisitions share the existing 250 ms wait
budget. The existing rename retry bound is 100 ms.

The daemon reads only published JSON files. Ordinary error paths remove the
temporary file, and existing daemon maintenance reclaims aged reservations
after a process failure. The one-hour age rule can also expire a stalled
publisher's reservation. An expired reservation cannot be promoted or recreated
by that writer.

Increasing the lock timeout would increase hook wait and still serialize disk
flushes. Uncounted staging would require a separate disk budget and cleanup.
The counted reservation reuses the current native and Python quota contract.

## Verification

- The deterministic native regression pauses a real publisher immediately
  before sync. The competing writer hit the admission timeout on red
  `91fa4a8` and published on green `692e1fa`. The green test also checks the
  shared file and byte footprint, quota rejection, and final temporary cleanup.
- `scripts/kaboost_audit_tdd.py` replayed both commits with the named Rust test.
- All 15 Rust tests, Rust formatting, Clippy, and the workspace package build
  passed. The first 18 focused Python cases for spool admission, quotas and
  maintenance passed before the Windows reservation-length correction.
- The parallel Watchdog run started before the Windows correction and ran
  alongside other checks. It finished with 2,151 passed, 1 skipped, and 9
  failures in subprocess, policy-response, and daemon-readiness cases.
  The spool quota and admission tests passed in that run.
- The final release adapter passed all 295 cases in `tests/test_rust_adapter.py`,
  `tests/test_spool.py`, and `tests/test_hook_install.py` with `-n 0` and
  `WATCHDOG_REQUIRE_NATIVE=1`, including all nine cases from the earlier run.
- The final parallel Watchdog run completed with 2,159 passed, 1 skipped, and
  1 failure in 265.71 s. All spool and native adapter cases passed. The
  Python-only `test_daemon_captures_a_hook_named_transcript` timed out waiting
  for transcript capture and passed in 3.44 s when rerun alone. WD-226 already
  tracks parallel failures of this test. This run does not establish the cause
  of the timeout.

## Installed instance

The real and MSIX adapter paths were resolved from a non-packaged process and
verified to be distinct. Both copies match the final release binary by SHA-256.
The core wheel was reinstalled and the owned daemon restarted using the
installation's config, data, and runtime arguments. It reported `running`.
`doctor` returned success with no warnings and a null adapter schema mismatch.

One labeled synthetic SessionStart per provider ran through the corresponding
installed adapter. Both events reached SQLite and both probe sessions were
purged. These checks cover the adapter-to-store transport. Real provider
callback coverage was outside this transport check.
