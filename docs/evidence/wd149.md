# WD-149: one queue and bounded daemon work

All observation sources now publish schema 2 records to the shared durable
spool: native hooks publish raw hook input, while Python dev commands and
post-response control observations publish prepared envelopes. One daemon drain
validates both forms and commits directly to Store. There is no runtime Inbox
publisher, reader, maintenance traversal, or diagnostic backlog. Historical
delivery fields remain readable. `inbox_bytes` is accepted with an explicit
deprecation warning and has no runtime effect.

Publication uses a temporary file, durable atomic replacement, stable event ID,
and the shared admission lock. Queue capacity includes unpublished temporary
files. Project registration, pause, payload limits, and capture policy are checked
again during ingestion. Events, receipts, facts, and state commit before tracker
updates, observation side effects, and queue unlink. Rollback restores state
caches. Receipt replay does not insert or apply state twice. SQLite remains
`synchronous=FULL`, secure deletion remains enabled, and each project has one writer.

## Ingestion and control measurements

Windows, Python 3.12.13; baseline revision `4ea781d`. Independent copies of one
frozen SQLite backup contain 36,968 retained events in 248,193,024 bytes, SHA-256
`34bace00ab9dce749e8a90f878e3553001e72d2251f263eaa92b7188e6c66d35`.
Following WD-172, each run drains 2,000 synthetic Codex tool events in one growing
session, including real commits and state replay. Both versions use the same
empty synthetic Git checkout. Fixture creation, backup, poll sleeps, transcript
enrichment, periodic maintenance, and provider calls are outside this timing.
Four authenticated loopback control clients each request an allow decision at
5 Hz during the drain, with the existing 300 ms adapter wait budget.

| Version / batch | Drain, seconds | Control p95, ms | Control timeouts |
| --- | ---: | ---: | ---: |
| Baseline / 25 | 127.44 | 143.38 | 6 |
| Unified / 1 | 419.90 | 229.92 | 109 |
| Unified / 25 | 30.13 | 177.12 | 0 |
| Unified / 50 | 22.78 | 170.97 | 0 |
| Unified / 100 | 18.51 | 120.34 | 0 |

The selected default is **100**: highest throughput among the compared batches,
with recovery/quota tests and the existing 500 ms control p95 requirement passing.
The reader still considers 100 records independently of the maintenance deadline.
Two independent default confirmations took **27.39 s** and **28.79 s**, respectively;
the latter includes caching successful checkout resolution within each window.
The final confirmation is **4.43x faster** than the baseline, with control p95
**163.47 ms**, two fail-open timeouts among 552 requests, and all 2,000 events
inserted without duplicates, rejection, or quarantine. These are individual runs,
not a confidence interval; the initial 6.89x result is not a guaranteed speedup.
Control latency percentiles cover successful responses; errors are reported
separately, and the final run does not establish zero control failures.

Raw results: [ingestion](wd149-ingestion.json),
[independent default confirmations](wd149-default-batch.json). Separate 200-event
profiles in the ingestion report show availability scans falling from one per
25-event batch to one per 100-event batch, and project Store opens from repeated
admission/snapshot opens to two opens for two reader windows. State replay occurs
once per affected identity per committed batch. Inclusive profile stages overlap
and must not be added. COMMIT time includes SQLite sync work.

Reproduction: `uv run python scripts/benchmark_ingestion.py --source-db
<frozen-events.sqlite3> --checkout <synthetic-checkout> --events 2000
--profile-events 200`. The script uses separate database copies for every batch
and profile pass, measures control traffic concurrently, and never invokes a provider.

## Maintenance and digest

One cooperative 200 ms allowance is shared across projects and queue temporary
cleanup per daemon tick. Round-robin scheduling and phase/cursor state survive
Store reopen; pending work resumes next tick. Admission cleanup spends the same
allowance, and returns a temporary outcome while reclaim remains unfinished.
Its queue input is retained without a loss counter. Only exhausted cleanup
permits final quota rejection. Budgets are checked between atomic operations;
SQLite commits, filesystem calls, and checkpoint steps can overrun cooperatively.
Retention preserves pins, removal order, and derived-table consistency.

The synthetic maintenance fixture has 12,000 events: 1,000 expired metrics,
1,000 expired content records, and 10,000 recent records. SQL cutoff selection
uses numeric received timestamps, including equivalent timestamps with different
UTC offsets. Expired metrics require no envelope parse; already stripped content
is skipped. Content mutations are grouped in bounded transactions (up to 32 rows
and a 1 MiB mutation target), avoiding one durable commit per record.

| Profiled cleanup | Baseline | Final |
| --- | ---: | ---: |
| Envelope parses | 13,000 | 1,000 |
| Total seconds | 0.674 | 0.550 |
| Slices | 1 | 3 |
| Longest slice, seconds | 0.674 | 0.199 |
| Commits | 1 | 69 |

An initial implementation reduced parsing but took 1.408 s and 1,037 commits;
the final grouped implementation corrects that regression. These cleanup times
include profiling overhead and are not an unprofiled throughput benchmark.

Provider-free digest construction on independent copies of the same retained
snapshot, fixed 2026-10-11 through 2026-10-18 UTC window:

| --- | ---: | ---: |
| Unprofiled seconds | 32.41 | 5.79 |

This is **5.59x faster**. Facts, items, and coverage match after excluding the
updated explanatory snapshot note; both result hashes are
`e3a5b7a0aca335a8bc62ba587ff0a09c5661f0f19a3e7f93999b83f85a85312a`.
Counts come from a separate profile pass. The single read-only snapshot closes
before a model call; causal context outside the reporting window, fixed token
shares, and unknown semantics are preserved. See [reader measurements](wd149-readers.json).

## Experimental transport

HTTP is an explicit `--benchmark-http` option in `scripts/benchmark_hooks.py`.
It starts only inside the isolated benchmark environment, calls the common
decision evaluator directly, and retains authentication, timeout, fail-open,
response evidence, and the common observation spool. It is absent from hook
installation and user configuration and disabled in normal operation.

| Synthetic adapter process call | TCP | HTTP |
| --- | ---: | ---: |
| First call, ms | 61.51 | 58.29 |
| Sequential p50 / p95, ms | 41.48 / 48.35 | 43.99 / 53.83 |
| Four clients p50 / p95, ms | 84.98 / 102.50 | 103.32 / 142.19 |

Each phase has 20 timed calls; with first call and eight warmups each transport
delivered 49/49 events, served 49 decisions, recorded zero errors/losses, and
preserved data after restart. The daemon was already running, so "first call"
means the adapter's first measured process invocation, not daemon cold startup.
CPU snapshots were 19.23% and 7.14%, respectively. This small sequential
experiment establishes no HTTP warm-latency advantage. These are synthetic calls
without provider validation. Raw [TCP](wd149-tcp.json) and [HTTP](wd149-http.json)
reports include delivery and loss accounting.

## Verification and live transition

Behavioral coverage includes native/dev/control publication, adapter readiness,
atomic publication failures, commit/unlink replay, rollback, pause, writer busy,
queue and project quotas, WAL reservation, pending cleanup, exact timestamp
retention, pins, restart, shared maintenance fairness, state recovery, digest
parse/query reuse and result equivalence, diagnostics shape validation, and HTTP
authentication/timeout/unavailable/default-off behavior.

Final local checks (2026-10-17): `uv run pytest` **1,652 passed, 1 skipped**
(91.71 s); `uv run ruff check .`, `uv run ruff format --check .`, `uv run ty check`,
and `uv build` passed. Native `cargo fmt --check`, locked Clippy with warnings as
errors, and locked tests passed (**14 tests**). The first full run found two
outdated expectations (the removed Inbox location and the additional retention
index); both modules passed 54 focused tests after updating those expectations,
then the full suite passed. These are local checks, not a claimed CI run.

An external one-shot script handles the sole live instance. It converts legacy
raw spool records and republishes legacy Inbox envelopes with their original
event IDs, deleting each Inbox source only after durable replacement. A
write-ahead manifest checks every migrated receipt as well as remaining legacy
files; an empty normal queue alone is insufficient. Full queues defer conversion;
malformed inputs use bounded content-free quarantine. No migration code or old
format reader is included in the project. A synthetic crash after replacement
and before source unlink was retried successfully: exactly two expected receipts,
no duplicate insertion, no remaining legacy input, and no secret in quarantine.
External checks also confirmed that a full queue defers both legacy inputs and
that a failed publication leaves the original schema 1 record and Inbox source
intact for retry.

The owned live instance was paused, its stable native adapter replaced, and the
verified wheel reinstalled without dependency changes, then restarted with its
existing config/data/runtime arguments. Installed daemon and native binary hashes
match the verified sources. Global hook definitions and trust records were not
modified; both hook files predate the rollout manifest. The deprecated local
`inbox_bytes` setting is still accepted and emits the documented warning.

The live legacy inventory was empty under pause: zero old spool records and zero
Inbox records, so no actual input conversion was needed. The external manifest
verification found zero missing receipts and zero remaining legacy files. This
does not replace the separate synthetic migration fault checks above.

The installed Codex adapter readiness probe returned `ready` for both spool and
Store admission and purged its synthetic session. A final read-only check found
the daemon `running`, no health reasons, zero queued files/bytes, five project
Stores with 700 session-state rows, and zero dirty Codex identities. HTTP discovery
is absent. Forty provider-free live control requests completed without error:
20 sequential requests had p50/p95 1.82/16.16 ms; 20 requests through four clients
had p50/p95 6.17/22.89 ms. This is a separate low-load channel check, not the
simultaneous ingestion benchmark or a provider action test.

The rollout wrapper initially read readiness fields at the wrong JSON nesting
level after a successful probe. Report extraction was corrected and final hashes,
receipt inventory, readiness, and live health verified without reinstalling.
Sanitized final checks are in [live verification](wd149-live.json).
