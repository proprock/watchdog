# WD-214 verification

Status: closed. Clean-clone acceptance and live update verified on Windows.

The native adapter now waits up to 250 ms for the shared spool admission lock. It can save a valid event after brief contention when capacity is available. The daemon drains the existing durable queue. The adapter still records `busy` when the wait expires. The Python publisher retains its 100 ms wait.

The owner accepted delayed processing during brief spikes to preserve valid events when capacity is available. In the synthetic Windows comparison, 100 ms and 250 ms builds each stored 40/40 events on an empty spool. With 3000 entries queued, they stored 35/40 and 40/40. With the lock held for 120 ms, they stored 21/40 and 40/40. With a 170 ms hold, they stored 0/40 and 40/40. The single-call median was about 16 ms in both builds. With the 170 ms hold, the 250 ms build's longest direct call took 219.5 ms. The probe used eight simultaneous calls and five trials per case without a running daemon or provider runner.
