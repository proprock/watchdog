# WD-212 verification

The [WD-184 clean-clone run](wd184.md) reported WinError 5 after the 100 ms
retry window while replacing `control.json`. A controlled Windows probe
reproduced the error with a reader held open, both with and without
`FILE_SHARE_DELETE`. The process that held the file in the original run
remains unidentified.

Windows control writes now use `FileRenameInfoEx` with replace and POSIX
semantics. Watchdog's Python daemon-state readers share delete access, as
the native adapter's standard-library file opens already do. A reader that
opened before replacement sees the old JSON. Opening the path after
replacement returns the new JSON. A reader that denies delete sharing still
causes a bounded error and leaves the previous state intact. Filesystems
that reject the extended rename use the ordinary replacement under the
same retry deadline.

- [Microsoft rename semantics](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/4217551b-d2c0-42cb-9dc1-69a716cf6d0c)
- [Rust default Windows file sharing](https://doc.rust-lang.org/stable/std/os/windows/fs/trait.OpenOptionsExt.html#tymethod.share_mode)

## Installed daemon verification on 2026-11-12

Reinstalled the `agent-watchdog` wheel using the active hook's paths. The
installed CLI paused the daemon while a delete-sharing reader held
`control.json` open. The old reader returned the prior running request and
a fresh read returned the new paused request. At 14:43:44 UTC, the daemon
