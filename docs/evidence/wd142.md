# WD-142 - Declarative rules, `rules` CLI, and built-in rules

## Delivered

- `rules/declarative.py`: pydantic models for a TOML rule (closed predicate set, six actions,
  cooldown, per-turn cap, expiry, one `$lower_tier` substitution) and `evaluate(rule, ctx, now)`.
  Regular expressions are limited to 512 characters, no nested quantifier, 64 KiB of input. A rule
  may only ask for an action the adapter renders on its event, so it cannot promise a delivery the
  adapter would drop. `parse_rule` raises `RuleError` for every problem and never echoes the body.
- `rules/registry.py`: built-ins from the package, user rules from `<config-dir>/rules/*.toml`,
  status derived from `[rules]` in `config.toml` (`approved`, `proposed`, `stale`, `disabled`,
  `invalid`), a cache keyed by file size and modification time, and the subscriptions the active
  rules need.
- `rules/engine.py`: evaluation order (built-ins, then user rules by priority), cooldown and per-turn
  throttle, project resolution only after a rule fired, the global and per-project
  `policy_intervene` switches, and the legacy `policy_intervene_same_model_subagent_spawn` alias.
- `rules/manage.py` and `agent-watchdog rules list|show|approve|reject|disable|enable|stats`.
  `approve` records the digest of the bytes it showed and re-checks it under the control lock.
- Built-ins (`rules/builtin/*.toml`): `subagent_same_model` (rewrite one tier down),
  `destructive_command` (ask), `repeat_same_input_same_output` (context), `stop_without_verification`
  (block, off by default).
- `state.py`: `edits_in_turn`, `verified_since_edit` (a boolean, no command text) and
  `trailing_repeats`.
- Daemon: `_Channel.sync` rewrites only the `subscriptions` of `socket.json` when the active rules
  change; the `control` payload gained `rule_version`, `text` and `delivered_at`.
- `analysis.control_findings` turns `control` events into findings, so `verdict`,
  `calibrate.py annotate` and `rules stats` handle them. They carry an `action`; `calibrate.py` and
  `wd122_report.py` keep such findings out of the precision gate and the confusion matrix, and
  `calibrate.py report` lists them under `action_rules`.
- `scripts/benchmark_hooks.py --event Stop|PostToolUse|PreToolUse`.
- Docs: `docs/rules.md` (new), `daemon.md`, `hooks.md`, `architecture.md`, `provider-compatibility.md`,
  `cli.md`, `config.example.toml`, `README.md`, `ROADMAP.md`.

## Decisions

- **The kill switches are independent.** TENETS asks for a global and a per-project switch that each
  disable every action. `Limits.policy_intervene` is checked as
  `config.defaults.policy_intervene and project.policy_intervene`, so a project cannot override the
  global one. The older `policy_intervene_same_model_subagent_spawn` keeps its override semantics
  and turns off the one built-in it named.
- **Same-model: rewrite, not deny.** WD-139 confirmed `updatedInput.model` on the `Agent` tool on
  Claude CLI. A rewrite is rendered as `permissionDecision: allow`, which also approves the call;
  that is acceptable for a model downgrade and is called out for user rules in `docs/rules.md`. The
  Claude desktop `Agent` rewrite is unevaluated.
- **State, not the database.** The rule reads `Context.session.coordinator_model`. A spawn made by a
  subagent has no coordinator model in its own state and is no longer evaluated (the old query
  compared it with the session's coordinator).
- **`log` is recorded only when no earlier rule delivered an action**, and its cooldown is spent
  when it is chosen. The audit's "log always written" is therefore weaker than stated; no built-in
  uses `log`.
- **Control findings are observations.** A finding with an `action` is excluded from the M2/M3
  precision gate, the confusion matrix and the false-negative count, in `calibrate.py` and
  `wd122_report.py`, and does not make a session a "session with findings" when sampling. This also
  changes how the existing same-model policy finding is counted by `calibrate.py`: it used to enter
  the gate lines as "observed, never reviewed".
- **Textual command matching.** `destructive_command` is a regular expression over the command, so
  `echo "rm -rf x"` asks too. `git checkout -- ./a.py`, `rm .env.example` and `git rm -r --cached x`
  do not. Each case is pinned in `tests/test_rules_builtin.py`.
- **Hook coverage.** The installer registers every Claude event with no matcher, so every event a
  rule may name is delivered; `tests/test_rules_builtin.py` asserts the rule events are a subset of
  `hooks.EVENTS["claude"]`.
- **No separate control hook entry.** `docs/architecture.md` once said the first subscription beyond
  the static one would need its own installed entry with a longer timeout. It was not built: a
  subscription shares the observation entry's 2 s timeout, and the adapter waits at most 300 ms
  and fails open. The measurement below is inside the 500 ms budget; WD-154 owns the quiet-host
  re-measurement and closes the question. The architecture text now says so.
- **Shell tools.** In the live stores about an eighth to a third of Claude's shell calls go through a
  `PowerShell` tool. The verification flag counts both `Bash` and `PowerShell` (found in review:
  without it a PowerShell test run would not count and the Stop rule would block a verified turn).
  `destructive_command` still watches `Bash` only; WD-160 covers PowerShell.
- **`insights/subagents.py` `FAMILIES`** is a membership list used to read a family out of a model
  id, not a ranking, so it cannot disagree with `[rules] tiers`; it was left as it is.

## Measurements

[wd142-subscribed-bench.json](wd142-subscribed-bench.json): two rounds each of `Stop` (unsubscribed),
`PostToolUse` and `PreToolUse`/`Bash` (subscribed, no rule matches), 20 sequential and 20 four-way
calls per run, on a host busier than during WD-140. Sequential p50 was 49.2-59.3 ms for `Stop`,
47.9-48.7 ms for `PostToolUse` and 46.9-49.2 ms for `PreToolUse`; sequential p95 78-107, 55-61 and
54-60 ms; four-way p95 121-123, 114-155 and 116-135 ms. The subscribed paths cannot be told apart
from the unsubscribed one at this sample size. All 57 events of every run were delivered.

## Checks

- On the final diff: `uv run pytest` 1190 passed, 1 skipped; `uv run ruff format --check .`,
  `uv run ruff check .`, `uv run ty check`, `git diff --check` clean; `uv build` produced the wheel
  and sdist, and the wheel lists the four `rules/builtin/*.toml` files. `native/` is untouched, so
  the cargo checks were not repeated.
- New tests: `tests/test_rules_declarative.py` (parsing, every predicate, rewrite, placeholders,
  expiry), `tests/test_rules_registry.py` (status, `stale`, `invalid`, cache, subscriptions),
  `tests/test_rules_cli.py` (approve and its refusals, the confirmation prompt, a file changed after
  review, reject/enable/disable, stats and precision), `tests/test_rules_builtin.py` (a replay of
  `tests/fixtures/hooks/claude.json` and of edit/test/stop, repeat and subagent sequences, plus
  a table of 29 commands that must ask and 24 that must not), and additions to `test_state.py`,
  `test_contracts.py`, `test_analysis.py`, `test_daemon.py` (kill switches, cooldown, a raising rule,
  `_Channel.sync`), `test_session_tracker.py`, `test_calibration.py`, `test_wd122_report.py`,
  `test_benchmark_hooks.py`, and two real-daemon tests in `test_rust_adapter.py` (a destructive
  command renders `ask`; a rule approved while the daemon runs is subscribed and rendered without a
  restart). Three existing same-model tests moved from `deny` to `rewrite`.
- During review a first version let a project's `policy_intervene = true` override the global
  `false`; a test asserted that. It was changed to the independent form above.
