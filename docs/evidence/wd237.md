# WD-237 evidence

The [Windows CI job](https://github.com/proprock/watchdog/actions/runs/43643390126/job/132595772215) rendered a nonempty `permit` response, then failed because the scratch store contained no callback. The CI traceback did not include native loss counters.

On local Windows, holding the shared spool admission lock for 600 ms while sending the policy reply reproduced the same assertion failure. The scratch spool contained the control envelope and the native loss counters showed `busy=1`. This identifies a mechanism that can produce the CI failure. The job's exact loss reason remains unknown.

The round-trip test verifies the rendered decision and both scratch records. It now queues the policy handler's control publication and executes the real publisher after the native adapter exits. This separates the two writes in this test so disk timing cannot make them contend with each other. If the callback is absent, the assertion now reports the scratch loss counters.

- The required-native probe module passed all 43 tests on Windows.
- An injected 600 ms delay inside the real control write passed with the native callback already present and all scratch loss counters at zero.
- A local full run before the test change passed the `permit` case and reported 2,193 passes, one skip and one separate failure in `test_native_clamps_a_huge_published_timeout`. The measured interval was 1.900825 s against a 1.9 s limit. WD-239 tracks that result.
- The full run after the test change passed the scratch-store tests and reported 2,190 passes, one skip and four failures in `tests/test_rust_adapter.py`: the timeout clamp took 2.001887 s, and the approved-rule profile round trips for desktop `PreToolUse` rewrite, HTTP `SessionStart` context, and desktop `Stop` block timed out or returned empty output. WD-240 tracks the profile cases. The four failing parameters all passed together with `-n 0` in 6.83 s.
- Ruff lint, Ruff format verification, ty and `git diff --check` passed. CI has yet to run against the fix.
- The Python publisher's lock scope was corrected in [WD-238](wd238.md).

## Follow-up on the parallel Windows failures

- WD-239 measured 1.600 s for the complete isolated invocation and 1.511 s from adapter start to callback construction. The test still enforces 1.9 s on the adapter interval, checks that the fake server received the request, and uses a separate process watchdog. The interval ends before spool publication.
- WD-240 reproduced empty decisions on both transports by delaying real policy evaluation by 350 ms with a 300 ms published budget. Both transports delivered the expected context with the same injected delay and a 1,500 ms test budget. The production timeout is unchanged. The profile matrix now publishes that test budget and reports request, decision and send timing for empty output or a subprocess timeout.
- The updated clamp, profile matrix and scratch-store test passed all 62 cases with four workers.
- The final full Windows run with the [Python publisher correction](wd238.md) passed with 2,195 tests and one skip.
