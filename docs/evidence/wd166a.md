The [official App Server documentation](https://learn.chatgpt.com/docs/app-server)
identifies generated schemas as specific to the binary version. This supplies
current-version interface evidence beyond CLI help; it is not implementation
proof. The standard generated `ThreadStartParams` exposes `baseInstructions`,
`developerInstructions`, `config`, `cwd` and `ephemeral`. `TurnStartParams`
exposes `disabledPluginIds` and sandbox/approval settings, but no global tool
allowlist or empty-tool-set selector. Its schema permits additional unspecified
properties; absence of a property therefore does not prove that every possible
undocumented control is rejected. No such control is accepted as a contract.
Dynamic tool declarations describe caller-provided tools, not removal of native
tools. The documentation distinguishes their namespaces from built-in tools.

The experimental schema was also generated and inspected. It adds `dynamicTools`,
named permission profiles and runtime workspace roots, but no documented complete
tool-removal field. `selectedCapabilityRoots` describes roots selected by a
hosting platform; it does not promise suppression of native tools or instruction
discovery. `config` accepts arbitrary keys, which is not evidence that any
particular undocumented isolation override works. `allowProviderModelFallback`
is a separate model-selection control, not an isolation mechanism.

Generated `ConfigReadResponse` includes `config`, `layers` and `origins`.
Its `ConfigLayerSource` explicitly enumerates packaged defaults, system, MDM,
enterprise-managed, user, project, session flags and legacy managed layers.
`ToolsV2` exposes only `web_search`. This confirms relevant boundaries exist in
the installed version's interface. Config provenance could aid a future audit;
it does not attest that every non-config loader and tool has been excluded. No
server was started and no effective user configuration was queried.

Inspection did not locate version-matched implementation source in the installed
bundle to establish native tool registration, complete loader behavior, or
correspondence to a published source revision. Embedded binary names such as
`update_plan` are discovery clues only;
their presence does not prove that the tool is registered on a given path.
The conclusion below is scoped to this executable and inspected interfaces,
not a claim that isolation is impossible in every Codex version or deployment.

The decisive limitation is the lack of a demonstrated **complete startup and
model-request boundary**, rather than absence of a particular help flag.
There is positive documentation for additional sources outside user config and
for managed hooks overriding local disablement. The inspected version's schema
also fails to supply the missing universal tool-removal contract. These findings
are sufficient to reject the proposed isolation recipe; they do not establish
that an undocumented flag or a different executable could never provide one.

## Invocation, scratch, environment and authentication decision

There is **no approved analysis argv** for this executable. Combining
`--ignore-user-config --ignore-rules --ephemeral --sandbox read-only` is rejected:
the flags respectively address user config, execpolicy rules, persistence and
command permissions, leaving the exclusions above unestablished.

A future viable mechanism must specify all of the following together:

1. Resolve and pin the executable/platform, displayed version and implementation
   or schema contract. Changed/unknown identities must not inherit approval.
2. Create owned scratch cwd/state outside every registered project, with no
   discovered ancestor instructions or project config. Bound the subprocess
   environment explicitly: home, config, temporary and integration discovery
   paths; credentials; provider endpoints; inherited application/IPC state.
   Do not mutate the parent's environment or active provider configuration.
3. Establish an explicit authentication transport and its managed-policy effects.
   Never copy an entire active Codex home. Credentials and any refreshed tokens
   must stay out of evidence, argv, logs and committed fixtures. Finish owned
   descendant cleanup before scratch/authentication cleanup (WD-166b).
4. Prove exclusion of every audited source before model input is sent, including
   system skills, all tool schemas and managed hooks. If managed requirements
   prevent the requested mode, refuse before integration initialization.
5. Keep the analysis timeout, cancellation and owned-process boundary distinct
   from daemon call budgets. Fail without provider fallback.

The concrete missing provider capability is an authenticated, content-only
invocation with a versioned guarantee of no instruction discovery, integrations,
hooks or model-visible tools, plus pre-inference effective-state evidence; or
equivalent version-matched implementation evidence and offline canaries proving
each exclusion. Incompatible managed policy must produce a refusal, not a local
policy bypass. A feature or schema change warrants a fresh audit and provider-free
checks before WD-166b; a successful model answer would not prove isolation.
