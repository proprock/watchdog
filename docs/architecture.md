# Architecture and contracts

Status: accepted design decisions. WD-003 [contracts](contracts.md), WD-004/007 [storage, retention, and redaction](storage.md), WD-005 [daemon](daemon.md), and WD-006 [hooks](hooks.md) are implemented. WD-008 provides the [observation CLI](cli.md); WD-009 adds Codex rollout-v1 usage enrichment; WD-010 adds deterministic, read-only shadow analysis and reports. WD-024 replaced the slow Python adapter with Rust, retaining the Python core and inbox contract. WD-027 made that adapter spool-and-forget: it durably spools each event, and the daemon resolves the checkout, builds the envelope, and admits it. WD-109 packages that Rust binary as versioned GitHub Actions release artifacts for the supported host matrix. WD-110 makes it the only production hook entry point: `hooks install` (WD-006) always requires one, never silently installing the Python CLI's `hook` subcommand, which remains only as a developer/test utility with a different, non-spooling delivery path (see "Processes and delivery" below). WD-115 moves the credential filter off the ingest path to the sanctioned-export boundary so the local store keeps the raw provider input. The implementation reports record exact verified boundaries. Date: 2026-09-16.

## Boundaries

A local single-user system, without a network service, centralized database, container infrastructure, or custom agent harness. M1-M4 implement one Codex adapter serving CLI and local desktop coding; the surface is an observation attribute, not a separate core. Claude coding support follows in M-Anthropic / WD-022, after WD-014 and before WD-015. Ordinary chats are outside scope. Keep provider-neutral events and a small adapter interface without a general plugin framework. If the surface cannot be reliably identified, record `unknown`.

```text
Codex hooks -- adapter --+                         single user core
                        +-- redacted spool -- drain --+-- project A inbox -- SQLite + artifacts
Claude hooks - adapter -+   (resolve + build here)    +-- project B inbox -- SQLite + artifacts
transcripts (optional enrichment) --------------------+
CLI -- project selection -- read-only queries / queued mutations
```

## Processes and delivery

- The native `agent-watchdog-hook` binary, invoked as `<codex|claude>` (the latter added in WD-022a) and the only production entry point since WD-110, reads JSON stdin and atomically writes the complete provider input plus raw `cwd`, `event_id`, and `received_at` to a durable spool (WD-027/107). The adapter removes only transport `cwd`; the local store keeps raw input and the credential filter runs only at sanctioned export (WD-115). The daemon's spool drain resolves the registered project/worktree, applies size and quota limits, normalizes known fields, retains provider metadata, and admits the envelope to the project inbox; an unregistered or since-removed `cwd` is discarded there. New top-level provider fields are retained and produce a bounded WARNING without their values. Content capture defaults to true with global/project opt-out, applied at drain. Do not run Git diff, analysis, or LLM calls inside a hook. Use the provider's no-op response: empty stdout for Claude; an empty JSON object was exercised for Codex, including Stop/SubagentStop. Never return feedback or control fields in observation mode, with one narrow, WD-014-approved exception: a `PreToolUse` call on Claude's `Agent` tool that the same-model-subagent-spawn deterministic policy rule denies prints the Claude `hookSpecificOutput`/`permissionDecision` deny contract instead of staying silent (WD-022b; see "M4 LLM/control design" below). Expected errors exit with code 0. WD-007 provides bounded persistent loss diagnostics.
- The Python CLI's `agent-watchdog hook codex|claude` subcommand shares the same provider name but is a distinct, non-production developer/test utility (WD-110): it resolves the checkout, builds the envelope, and enqueues directly in the hook process (`hooks.py::observe`), with no spool stage. `hooks install` never installs it; production hooks always invoke the native binary above.
- The adapter stamps the envelope ID and received time when it spools; the drain preserves both, so a replayed spool record yields the same envelope. Reprocessing is idempotent. Deduplicate repeated provider events only when a stable native ID is available, not merely by text hash.
- Optional daemon-wide pipeline telemetry stamps bounded stage-entry times and queue samples into envelopes after redaction. It can be disabled without changing the spool/inbox/SQLite delivery contract; it is global because native hooks do not resolve projects.
- The hook ensures a detached `agent-watchdog daemon run` starts if the core is unavailable. POSIX: a new session; Windows: a detached process without a window. Do not inherit the harness stdin/stdout/stderr handles.
- The Python core records bounded operational decisions in a global data-directory log. Its records use fixed codes, fixed provider names, a shape-bounded `error_type` (exception class name or internal failure code) and field name, and local Watchdog UUIDs only; prompts, paths, provider/session IDs, commands, tool output, payload values, exception messages, and tracebacks are excluded by default. Opt-in `[defaults] log_detail = true` appends one de-identified, 200-character `detail="..."` error string (credential forms removed, paths retained) for local debugging; it stays off for shipped defaults, exports, and shared reports. Logging is best effort and cannot change hook output or delivery.
- One OS-backed lock per user, held for the core's lifetime. Competing starts fail to acquire the lock and exit. PID/heartbeat are diagnostics, not the sole exclusivity mechanism. Never kill an unrelated process after PID reuse.
- The core lives until logout/stop; the next hook recovers a crash. This does not guarantee continuous operation without new events. Validate Codex CLI/desktop lifecycle on Windows in WD-005 and M1 acceptance; WD-022a lands the Claude observation adapter and installer; its live gate is met (see [verification](verification.md#wd-022a-claude-observation-gate-met)) across a CLI Pass A re-run and a supervised desktop pass; Claude enrichment, lifecycle beyond observation, and guidance/control stay in WD-022b; access to macOS/Linux hosts and compatibility verification are deferred to M5 / WD-019. Keep platform-specific launch/lock behavior isolated. Some process containers/job objects may restrict detachment; provide explicit user autostart as a fallback when that limitation is demonstrated.
- `daemon stop` sets a persistent pause and stops the core through the control inbox; new hooks neither start it nor accumulate events until `daemon start`. A crash does not set pause. `daemon status` distinguishes paused, running, unavailable, and degraded.
- The core commits events sequentially into each project's SQLite database; delete inbox entries only after commit. The spool drain is the same shape one stage earlier: delete a spool record only after its inbox write, and a crash in between replays safely because the envelope ID is stable. Put malformed records in bounded quarantine without blocking the entire queue.
- Poll inboxes every 250 ms while active, backing off to 2 s when idle. Store event time and received time separately; do not promise global ordering across processes. Late events recompute affected aggregates.
- Hooks do not wait for analysis or core readiness. Target full-call p95 latency of at most 250 ms on the measured machine, with a 2 s hook timeout. Measure Python startup and writing separately; do not hide their cost through async configuration.

## Projects and storage

Resolve user config/data/runtime directories with platformdirs. User TOML contains the registered project list and defaults. `project add <path>` explicitly registers a UUID, canonical root, and Git common-dir; worktrees resolve to that UUID. A separate clone gets a separate UUID. Identify non-Git projects by canonical root. Moving a project requires explicit `project relocate`, not merging by remote URL.

One directory per UUID: SQLite (WAL), inbox, artifacts, and quarantine. The registry contains no aggregate analytics. Store large raw outputs as separate artifacts; the database holds references, fingerprints, and bounded excerpts. Do not recursively scan user files: the transcript reader opens only an absolute Codex path previously recorded from a Codex hook and validates it against the observed session.

### Local fidelity and redaction

Watchdog observes one user's own coding sessions, whose prompts and outputs have already been sent to the provider, and it analyzes them locally without transmitting anything off the machine without the user's sanction. The per-project store is therefore not a sharing surface: it keeps the raw provider input, subject to `capture_content` and size limits. The credential filter is a bounded pattern matcher that can over-redact; it must not be the reason the only local copy of a session loses signal. WD-115 makes it an export-time transform: ingest and drain persist raw input, and the filter runs only when `inspection` writes an export intended to leave the machine. Collection scope (explicit registration, `daemon stop`, retention) still bounds what is kept.

The core is the only database writer. The CLI uses read-only connections; WD-011 labels, pins, and purges and WD-012 finding verdicts pass through a bounded control inbox with request IDs and acknowledgments. Lifecycle controls remain a single-slot desired-state file. Read-only reports and exports work while the core is stopped. Require a schema version and sequential migrations; reject unsupported newer schemas with a clear error and no overwrite.

Defaults are configurable in user TOML, with overrides by project UUID:

| Setting | Value |
|---|---:|
| Content / aggregates and labels | 30 / 180 days (`0` disables time expiry) |
| Total project quota, including WAL/inbox/artifacts | 2 GiB |
| Inbox within the total quota | 64 MiB |
| Maximum persisted event payload | 1 MiB |
| Process logs | 5 files of 10 MiB each |

Retention is a disk-budget control, not a privacy control: the data is the user's own, kept locally. Setting a day count to `0` disables time-based expiry for that class; the project quota and degraded-state loss counters still bound growth.

Delete expired content first, then old unpinned content, then old unpinned sessions. Pin protects against deletion, not quota accounting: if space cannot be reclaimed, stop accepting content/events and report degraded status with loss counters. Never silently delete pinned data. Reserve space for checkpoint/diagnostics; bound concurrent inbox writes with a short project lock. Account for auxiliary files; SQLite cleanup uses incremental vacuum/checkpoint support. Never delete existing vendor transcripts. See the implemented policy and operational limits in [storage](storage.md).

## Normalized events

Versioned envelope: `schema_version`, `event_id`, `provider`, `provider_version` (nullable), `surface`, `project_id`, `checkout_id`, `session_id`, `agent_id`, `parent_agent_id`, `turn_id`, `native_event_id`, `kind`, `occurred_at`, `received_at`, `source`, `payload`, and `availability`. Unavailable identifiers are nullable; do not invent them. Distinguish root sessions from subagents; leave unresolved ownership unassigned instead of mixing counters.

Kinds: session/turn lifecycle, tool start/finish, compaction, subagent lifecycle, waiting/interrupt, usage, and observation gap. Allow provider-specific payloads in a namespaced field. Preserve unsupported versions/events as unknown with a bounded payload. CLI JSON export uses the same versioned envelope; this is the first external data interface.

Hooks are the primary source. Transcript enrichment (`codex-rollout-v1` and, from WD-022b, `claude-transcript-v1` for the session and each subagent `agent_transcript_path`) runs only in the daemon from hook-provided absolute paths; it never persists transcript content. Durable per-source reader state handles partial lines, truncation, rotation, and resume. A transcript line is read whole, across read windows, up to 32 MiB (WD-130: real Codex `item_completed` lines reach 6.7 MiB, and the former 1 MiB limit stopped such sources for good). A longer line is skipped with a `transcript_line_oversized` gap. A Claude response too large to hold open is emitted with its last-seen usage and a `claude_response_oversized` gap, because that value may undercount. No line is dropped silently. Bind readers to verified fixtures/versions. On a format change, disable only that enrichment source and persist an observation gap. Correlate usage by response, turn, and session IDs. A Codex usage event is identified by its session and `response_id`, never by the transcript path spelling or line offset, and the reader skips a response already stored for that session under any event ID (WD-128: Codex reports the same rollout as both `C:\...` and `\\?\C:\...`). A Claude usage event is likewise identified by its conversation, agent, and `requestId`, and the Claude reader skips a request already stored for them (WD-129). A Codex hook fired inside a subagent reports the subagent's own rollout (`rollout-<time>-<thread id>.jsonl`) under the parent session. The reader reads it as that subagent (usage `agent_id` = thread id) once `session_meta` names the thread and the parent session; otherwise it records a `subagent_meta_mismatch` gap (WD-131). Such usage inherits a model or effort only from the same agent's hooks. Rows the earlier path-keyed reader stored twice stay in place, because stored events are authoritative. Usage reads (`usage`, `--price`, `report`, `export`, `insights`) count each stored response (its `native_event_id` within a conversation) once, taking its first stored copy. Codex uses `thread_token_usage` as the sole cumulative scope and derives fieldwise deltas, never summing the three provider snapshots. Claude `message.usage` is per response, not cumulative, and is repeated on every content block; emit one `usage` event per distinct `requestId`, store each Anthropic counter raw, and never synthesise a `total_tokens` Anthropic does not report. The reported value can grow across a response's own blocks (confirmed on real subagent transcripts: `output_tokens` commonly grows from single digits to its true final value); a response is held open until a block reports a non-null `stop_reason`, or is treated as closed by a later, distinct `requestId` superseding it, so the emitted counters are the final value, not the first. Content-free scans of real transcripts found this growth only on subagent (sidechain) responses — main-conversation responses always repeat the same, already-final value across their blocks — and found a small minority of subagent responses that never report a `stop_reason` at all; those flush with their last-known value once the source stops growing (a single read window with no new bytes), an accepted residual limitation shared with the existing partial-line tail cap (both bounded at well under the `transcript_sources.tail` column's 1 MiB limit). An event id already stored under the prior first-block-wins behavior is never re-emitted with a different value under the same id; it keeps its original value, another accepted, explicit limitation rather than a receipt-identity conflict. Input/output/cached tokens are independently observed or unavailable. A Claude subagent `usage` row resolves to its parent conversation and carries the subagent's `agent_id`. Keep estimated and measured values separate. Subscription cost cannot be derived from token counts; defer monetary estimates.

## Analysis and reports

- Distinguish turn completion, session stop, and verified task outcome. Users label outcomes: success, partial, failed, abandoned, unknown. Task type is a free-form label with suggested bugfix/feature/refactor/docs/research values. A manual review adds a separate progress judgement (progress, slow, stuck, externally_blocked) and a per-finding verdict (true_positive, false_positive, uncertain); these are calibration inputs and no rule reads them.
- M2 rules: repeated command+outcome, identical error fingerprint, repeated failing-test set from comparable runs, compactions, and output size. Preserve rule versions, evidence IDs, counts, and explanations. An initial repetition threshold of 3 is a shadow-analysis hypothesis, not an intervention command. WD-010 implements these rules in the offline `report` view; findings remain observations, not control requests. Each finding also carries a `fingerprint` over its sorted evidence identifiers so a manual verdict survives recomputation; `diff_oscillation` evidence still belongs to a checkout, not a session, and its manual verdict stays keyed by checkout (WD-013).
- Do not normalize commands aggressively: `pytest -x` changes the observed failure set. Compare test deltas only with matching target/configuration and completed results. The first structured parser covers pytest/JUnit; other outputs provide best-effort signals, not proof of acceptance.
- Compute debounced Git diff fingerprints per checkout in the core. Since WD-121 (2026-09-30) a fingerprint covers unstaged and staged tracked changes plus untracked, non-ignored files, bounded and unknown on any failure ([coverage](storage.md#checkout-fingerprint-coverage-wd-121)); earlier snapshots covered unstaged tracked changes only, under the same `wd-010.v1` rule version. Concurrent agents/user edits make attribution uncertain. A->B->A is a signal, not proof of a stall. Snapshots must not modify the index or worktree. WD-118 narrows which sessions a checkout-wide oscillation is *reported to*: `inspection.snapshots_for_checkouts` tags each snapshot with the sessions whose observed turn window (`turn.start`/`turn.end`) covered its capture instant, and `analyze` only surfaces the finding to a session in that set. An oscillation whose three snapshots span more than one session keeps its existing "uncertain" attribution — a concurrent editor is not excluded. An oscillation with no session at all attributable (no turn boundary observed for the checkout) still surfaces to every session touching the checkout, matching the prior behavior, because narrowing on no evidence would manufacture false precision rather than reduce it.
- No universal no-progress score based on missing events. Distinguish observed, inferred, and unknown for every finding; waiting for a user/tool or incomplete data is not a stall. Exit code 0 does not automatically reset signals.
- CLI reports show timeline, coverage/gaps, active time separately from wall time, repetitions, available usage/compaction, and labels. Without evidence of interval start/end, active time is unknown.
- Export selected sessions as a Markdown summary, JSONL events, a manifest with versions/completeness/redaction, and a prompt template for manual LLM analysis. Export is the redaction boundary: the credential filter is applied here, over the raw stored input (WD-115). No automatic transmission. Clearly mark trace content as untrusted data; a content review before external sharing is recommended, not an enforced gate.

## Later extensions

Keep intervention separate from observations: proposal, evidence, required capability, expiry, and delivery receipt. M0-M2 do not implement placeholders for it. Begin with shadow calibration, then opt-in guidance at a native safe boundary. Stop continuation is not a hard pause. Do not assume App Server can attach to arbitrary desktop sessions: investigate session ownership/attach separately first.

## M3 guidance policy (WD-013)

This section is the M3 decision gate: it fixes the delivery mechanism and applies the WD-012 calibration to select rules. It is a design decision, not an implementation; M3 is only built once a rule actually clears the gate below.

**Mechanism, for whenever a rule qualifies:**

- Observe remains the default for every project; guidance requires explicit per-project opt-in, separate from the existing `content_capture` opt-out. A global kill switch stops delivery immediately regardless of per-project opt-in, with no residual nudge in flight.
- A delivery record is distinct from an observation: it carries the source finding's evidence IDs, the capability it required, an expiry, and a cooldown. At most one nudge per blocker fires until new evidence appears for it; a blocker that keeps re-observing the same evidence does not re-notify.
- Record `proposed`, `delivered`, and `response_observed` as three separate facts. Delivery is not acceptance: a nudge the user ignores, argues with, or contradicts is not itself evidence the finding was wrong, and a nudge followed by a change is not proof the finding was right. Advice-acceptance measurement is a separate, later analysis, never folded into precision.
- Provider-specific safe delivery only: a nudge is injected solely at a boundary a provider adapter can support without altering control flow (see the CLI/hook contracts); an unsupported provider/surface combination stays observe-only.

**Rule selection, applying the gate to [wd012-calibration.md](evidence/wd012-calibration.md):**

The M2 release gate is at least 90% session-scoped precision on a declared, disclosed-sample-size dataset (ROADMAP M3). Generated from the 24-session frozen cohort (`scripts/calibrate.py report`, `wd-012.calibration.v3`):

| rule | observed | precision | gate result |
| --- | --- | --- | --- |
| `repeated_tool_outcome` | 8 | 25.00% (2 TP / 6 FP) | fails; well below 90% at a reviewed sample of 8, not a borderline small-sample case |
| `identical_error` | 0 | null | fails; zero observations in this cohort is no evidence, not a pass |
| `repeated_test_failure` | 0 | null | fails; zero observations in this cohort is no evidence, not a pass |
| `diff_oscillation` | 8 | unreviewed (checkout-scoped) | not eligible for session-scoped delivery; still checkout-scoped by decision, though WD-118 has landed the attribution mechanism a future gate re-run would score against |

**Decision:** no `wd-010.v1` rule is selected for M3 delivery. The mechanism above is specified so a future qualifying rule has a fixed target to implement against, but no code path delivers guidance today; all four rules stay observe-only, matching the M0-M2 boundary already in place. The 4 recorded false negatives (slow sessions with no session-scoped finding) mean even a precision fix would leave recall gaps; do not read a future precision pass as sufficient on its own.

**Re-opening this gate:** a rule is promoted only by a fresh `scripts/calibrate.py report` run showing it at or above 90% precision with its sample size, not by arguing around the numbers above. WD-118 changed `diff_oscillation` attribution (`inspection.snapshots_for_checkouts` narrows which sessions a checkout-wide oscillation is reported to, using observed turn windows) and demonstrated the fix with offline tests (`tests/test_analysis.py`, `tests/test_observation_cli.py`); it did not itself flip `CHECKOUT_SCOPED_RULES` or re-run calibration against the live store, so the numbers in this table are still the pre-WD-118 baseline. Re-run `scripts/calibrate.py sample`/`report` against the live store, and decide separately whether the now-attributable rule should move out of `CHECKOUT_SCOPED_RULES`, once any rule-logic fix lands or the live cohort has grown past the current 24 sessions.

## M4 LLM/control design (WD-014)

This section is the M4 execution/control decision gate: it fixes how a semantic-judge LLM call would be invoked, bounded, isolated, and escalated, if and when a future trigger is authorized, and separately fixes a rule system for deterministic policy rules that need no calibration. It is a design decision, not an implementation; nothing below installs a hook, calls a model, or changes runtime behavior.

**Execution mechanism:** local analysis calls the provider's own CLI in headless mode (`claude -p ...` / `codex exec ...`), not a raw provider API client — this reuses the user's already-authenticated CLI/subscription, avoids adding an API-key/secrets surface, and reuses the existing no-window subprocess wrapper (`src/agent_watchdog/_proc.py::run`/`popen`). A hosted API path is out of scope until a CLI limitation is demonstrated. The call happens only from the daemon or an explicit user-run CLI command, never inside a hook (existing invariant above: "Do not run Git diff, analysis, or LLM calls inside a hook"). Every call records provider name, CLI binary path, and version (`--version`) as provenance, alongside the evidence bundle sent and the structured response received.

**Opt-in and kill switch:** disabled by default everywhere. A project needs an explicit opt-in flag, `semantic_judge_enabled` (default `false`), distinct from `content_capture` and the WD-013 `guidance` opt-in. A global `semantic_judge_enabled = false` at the top-level `[defaults]` scope stops all future calls immediately regardless of a project override (mirroring how `capture_content` composes today); in-flight calls finish or hit their timeout, never force-killed mid-write.

**Budget and timeout — explicit, named config settings, not hidden constants:** `semantic_judge_timeout_seconds` (default `60`, generous next to the 2 s hook timeout since this never runs in the hook path) is the per-call wall-clock timeout; exceeding it kills the call and records `timeout`, with no automatic retry. `semantic_judge_daily_call_budget` (default `5`) is the per-project daily call cap; exhausting it refuses new calls with a clear error rather than queuing or silently skipping. Both settings live under `[defaults]` in `config.example.toml`, overridable per project under `[projects.overrides]`, the same mechanism `capture_content` and the byte/day limits already use; WD-014 fixes their exact names and defaults now, but neither is implemented or added to `config.example.toml` yet, since no code reads them. Budget exhaustion, timeout, nonzero exit, or malformed output all record as `unavailable`, never as a `progress`/`stuck` verdict, and never block or delay hook responses.

**Exclusion of the product's own analytical sessions (recursion control):** the spawned CLI call runs against an isolated, throwaway config/home directory with Watchdog hooks NOT installed into it, not merely tagged or filtered after the fact, so the call has no hook wiring through which to recurse into any project's inbox. If isolation cannot be established (for example, the CLI needs the user's real config to authenticate), the call is refused rather than run un-isolated. The bundle sent to the model never includes Watchdog's own source, logs, or database.

**Facts/evidence bundle and structured output:** the input is a compact bundle built from already-stored evidence (findings, evidence IDs, fingerprints, bounded excerpts), never a raw transcript re-send; it reuses the existing WD-011 export-bundle shape (`inspection.export_sessions`) as its base format. The output is a structured `progress|uncertain|stuck|blocked` judgment plus free-text rationale; a summary is never treated as objective verification, and it never overwrites an M2 deterministic finding.

**Escalation ladder and human gate:** the ladder is advisory -> replan request -> read-only second opinion -> question for the user, and a caller need not walk every step for every signal. A "question for the user" delivers at the same safe hook boundary as the WD-013 guidance mechanism (a textual nudge) — explicitly not a forced pause/resume; Watchdog never auto-grants an approval. An actual pause/resume/attach capability requires a confirmed adapter contract; none exists today for Codex or Claude, so this stage stays theoretical until WD-015 (App Server spike) demonstrates one.

**Amendment (WD-123, manual insights):** the first implemented model call is the user-run `agent-watchdog insights` command ([cli](cli.md#insights)), and it revises three points above for that manual path only.
- **Isolation.** It comes from `claude -p` flags rather than a throwaway config home. The user's subscription login lives in that home, so a separate one would break authentication. `--safe-mode` disables hooks, CLAUDE.md, skills, plugins and MCP servers while keeping auth. `--setting-sources ""`, `--strict-mcp-config`, `--tools ""` and `--no-session-persistence` remove the rest. The call runs from a scratch directory outside every registered root.
- **Refusal.** The WD-014 refusal clause still applies: without `--safe-mode` the call is refused. A live probe confirmed that no analysis session reached any project store (see [verification](verification.md#wd-123-insights-live-probe)).
- **Opt-in and limits.** For this manual command the explicit invocation is the opt-in, replacing a per-project `semantic_judge_enabled`. Its kill switch is `insights_llm_enabled` in `[defaults]` or project overrides. `--timeout` (default 600 s, well above a measured 148 s call because a window-scaled bundle adds input time) replaces `semantic_judge_timeout_seconds` for the manual path. The bundle budget scales with the context window the model reported on its previous call, remembered per model in the data directory. No daily budget applies to a call the user starts by hand.
- **Reserved names.** `semantic_judge_enabled`, `semantic_judge_timeout_seconds` and `semantic_judge_daily_call_budget` remain reserved for any future automatic trigger.
- **Bundle.** It is a redacted evidence bundle, an export boundary under WD-115, ranked and fitted to a token budget. It is not the raw `export_sessions` event dump: real sessions exceed any context window (p90 per-session content was about 1 MB on the live store).
- **The judge itself (WD-126).** `insights session` is this section's manually invoked second opinion. It returns the structured `progress|uncertain|stuck|blocked` judgement with a rationale, grounded evidence IDs, and a next step, and it never overwrites or stores anything. `scripts/calibrate.py annotate` offers it only on request (`s`), labelled "LLM suggestion, not a verdict". No automatic trigger exists; the re-opening conditions below still govern one.

**Deterministic policy rules (no calibration required):** distinct from the M2/M3 statistical rule set, a policy rule encodes a structural fact that is true or false by construction — for example, a subagent's resolved model ID equals its coordinator's, using the per-turn model resolution WD-022b delivers — not a probabilistic judgment about progress or stalls. The WD-013 90% precision gate does not apply to this class; correctness is definitional, so a policy rule may be enabled without a calibration cycle. Every policy rule declares one action: `log` records a full-fidelity finding through the normal event/finding path (subject to `capture_content` and retention/quota, redacted only at export per WD-115) — the triggering fact, its evidence IDs, and the exact tool input/prompt passed — through the normal finding path rather than the bounded operational diagnostic log, which deliberately excludes prompts and content; `intervene` additionally denies or alters the current call at the hook boundary itself, only where the provider adapter has a confirmed blocking capability; `both` logs unconditionally, then attempts `intervene`. The first rule, shipped as the concrete example informing this design and not an M2 shadow rule, is same-model subagent spawn (a subagent's resolved model equals its coordinator's), with action `both`: `log` always records the launch fact and the subagent's exact prompt/tool input as evidence; `intervene`, confirmed capability today on Claude only, at `PreToolUse` (already mapped to `tool.start`, see "Normalized events" and `docs/hooks.md`), denies the tool call and returns an error telling the caller to downgrade the subagent's model tier — the one narrow, adapter-confirmed exception to the "hooks do not block" invariant below. On Codex, or any provider without a confirmed blocking capability, `intervene` degrades to `log` automatically (the tool call proceeds unmodified) plus a bounded warning recorded in the same finding, so the capability gap stays visible for later review rather than silently dropped. Rules are declared as `{name, condition, action}`; adding a new deterministic policy rule is a config/implementation change, never itself requiring a fresh WD-013-style precision gate, which applies only to a rule whose condition is a probabilistic judgment.

This design requires one narrow, explicitly scoped exception to the Invariants section's "Observation hooks do not block, continue a turn, or inject model context": a deterministic policy rule (never a statistical M2/M3 rule) with a declared `intervene`/`both` action may deny a `PreToolUse`-equivalent call and return an error, only on a provider/adapter with confirmed blocking capability (currently Claude `PreToolUse` only). Every other hook path, and every provider without confirmed capability, remains observation-only, with `intervene` degrading to `log` plus a recorded warning rather than silently doing nothing; see TENETS.md.

**Decision:** the policy above (CLI-mode calls, explicit opt-in, kill switch, the named `semantic_judge_timeout_seconds`/`semantic_judge_daily_call_budget` config settings, isolated non-observing analysis sessions, bundle/output shape, ladder/gate boundaries, the deterministic policy-rule system, and the narrow invariant exception) is fixed as the target for whenever M4 is implemented. It does not itself authorize any automatic semantic-judge call: applying it to the M2/M3 results already recorded ([wd012-calibration.md](evidence/wd012-calibration.md) and the WD-013 gate table above), no M2 rule cleared the 90% precision bar, so there is no calibrated trigger to feed an escalation ladder today. M4 therefore ships, if at all, only as a manually user-invoked "second opinion" (bundle -> CLI call -> structured judgment in a report), never an automatic trigger from an M2 rule, until a rule is separately promoted. The deterministic policy-rule system and its first rule are fixed by this decision but not implemented by it; implementation is separate future work, most likely folded into WD-022b, since detecting "subagent model equals coordinator model" needs the per-turn model resolution WD-022b already delivers.

**Re-opening this gate:** an automatic statistical (M2-rule-triggered) escalation path opens only when a future WD-013-style gate re-run promotes an M2 rule at or above 90% precision with disclosed sample size, or a separate future decision defines semantic-judge-specific triggering criteria independent of the current rule set. This re-opening clause does not gate deterministic policy rules, which may be added or enabled at any time as a config/implementation change since their condition is not a statistical judgment. A real pause/resume human gate for the semantic-judge ladder opens only once WD-015 demonstrates a concrete, adapter-verified attach/steer/interrupt contract; this is separate from the already-decided `intervene` exception for policy rules, which does not wait on WD-015. The budget/timeout defaults above may be revised once real latency/cost data exists from the manual-invocation path.

**Implementation (WD-022b, the `log` half):** `agent_watchdog.analysis.same_model_subagent_spawn` implements the first deterministic policy rule's unconditional `log` step, under its own `POLICY_RULE_VERSION` ("wd-014.v1") separate from the M2/M3 statistical `RULE_VERSION`. Each finding carries `"action": "both"`, the rule's own WD-014-declared action (not merely "log": this function only performs the log step itself, but the finding names the rule's actual configured action; the `intervene` attempt happens separately and synchronously, below, and is not itself recorded onto the finding), one finding per subagent spawn (`agent_id`), not per usage event (a subagent's own response can produce several usage rows). The model comparison walks a session's already-persisted envelopes directly (each Claude usage event already carries its own observed `payload.claude.model`, from `transcripts.py`'s `claude-transcript-v1` reader), ordered by `occurred_at` (the true API response time) rather than `received_at` (ingestion time): a subagent transcript is registered only at `agent.end` and enriched afterwards, so its usage rows can be received long after a later coordinator model switch even though they occurred before it, and only `occurred_at` order compares against the model genuinely active at the time. The most recently occurring coordinator usage event's model (`agent_id is None`) is compared against each subagent usage event's own model (`agent_id` set); a subagent whose model has not yet been observed is never compared, not treated as a false match. Evidence is the matching `agent.start` event (the launch fact) plus the first matching subagent usage event; the spawning tool call's own prompt/tool input, on its `PreToolUse`/`tool.start` event, carries no `agent_id` yet at that point and cannot be linked here — the "exact tool input/prompt" evidence the policy-rule design describes is not available at this layer for this rule; a future `intervene` implementation instead compares synchronously at `PreToolUse` time, where the tool input is directly at hand. This reuses the model each response already reports, rather than schema-v6's `event_facts`/`_inherited_config` inheritance table, which resolves a *missing* model by carrying one forward — not needed here since a `usage` event's own model is always directly observed by construction. `intervene` (the Claude-`PreToolUse`-only deny path) is implemented separately (below). The `both` action's degrade-to-`log` behavior on non-Claude adapters is not implemented, and cannot be reached today: `same_model_subagent_spawn` itself only ever evaluates `provider == "claude"` events, since Codex usage events carry no per-subagent model attribution this rule could compare -- there is no Codex finding for a degrade warning to attach to, not a degrade that silently produces one anyway. Codex's adapter correspondingly has no policy-socket branch at all and always takes the unmodified fire-and-forget path, which is a `provider`-level exclusion, not an instance of the WD-014 degrade mechanism.

**Implementation (WD-022b, `intervene`):** the native adapter never gained a general blocking round-trip; WD-027's "spool-and-forget" design (fire-and-forget, no listener anywhere) stands for every other event and provider. Exactly one narrow addition exists: while the daemon is running, it also runs a loopback-only (`127.0.0.1`, binding wider would trigger a Windows Firewall prompt for no benefit) TCP listener on a background thread, publishing `{schema_version, pid, port, token}` to `<data>/policy/socket.json` -- the same discovery-file pattern `spool/limits.json` already uses, with a random per-instance token added since this file, unlike the spool limits, gates a real decision. The Rust adapter's `observe()` (`native/src/main.rs`) checks cheaply first -- Claude, `PreToolUse`, tool name `Agent` (confirmed from real transcripts; not `Task`), and an explicit `tool_input.model` present -- so every other hook stays on the unchanged, zero-cost path; a subagent spawned without an explicit override (the common case, resolved later from `.claude/agents/*.md` frontmatter or inherited) has no model visible here at all, an accepted, documented recall gap. Only when all of those hold does it read `policy/socket.json` and connect, with a strict `connect_timeout` plus read/write timeouts (150 ms each; a plain blocking `connect` against a stale port can retry for seconds on Windows, which `connect_timeout` avoids), asking the daemon a single JSON question (`cwd`, `session_id`, the alias in `tool_input.model`) and getting `allow`/`deny` back. The daemon resolves `cwd` through the registry (read-only; the adapter has not resolved projects since WD-027) and looks up the session's most recently *occurring* (`event_facts.occurred_at_us`, falling back to `received_at_us`) `agent_id IS NULL` Claude usage row's `model` from a read-only connection (`inspection.database`, not `Store`, to avoid contending with the poll loop's writer lock). The alias is only ever a model family name (`sonnet`/`opus`/`haiku`/`fable`) at this point, never the coordinator's full resolved id (e.g. `claude-opus-5-5`), so the comparison (`agent_watchdog.analysis.model_family_matches`) matches at the hyphen-delimited family segment, not exact equality. A candidate already at the lowest known tier (`haiku`) is never denied either, regardless of a match: the deny reason tells the caller to downgrade, and there is nothing lower to downgrade a `haiku` spawn to. Anthropic ranks `opus > sonnet > haiku`; the fourth alias, `fable`, has no established public rank relative to the other three and is deliberately left out of this floor rather than guessed (`agent_watchdog.daemon._LOWEST_TIER_ALIASES`). On `deny`, the adapter prints the verified, currently-supported Claude contract, `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}`, on stdout with exit 0 -- the one path where the Claude adapter ever writes meaningful stdout, since every other Claude path stays silent (hook stdout otherwise reaches the model's context on `SessionStart`/`UserPromptSubmit`). Every failure -- missing/stale/malformed socket file, refused or timed-out connection, an unresolved project, no database, no observed coordinator model, a mismatched token -- resolves to `allow` independently; nothing here fails closed, matching "Watchdog failures must not stop the harness." The event is still spooled unconditionally on every path (the `log` half of `both` always fires) regardless of the decision. The socket is torn down, and its discovery file removed, on every daemon exit path (pause included) via the same `ExitStack` that owns the daemon lock, so a stale file left by an unclean exit is, at worst, a dead port a later process might reuse -- caught by the token check, never a false deny. Verified end to end with a real adapter binary against a real running daemon (`tests/test_rust_adapter.py::test_native_deny_round_trips_through_a_real_running_daemon`), not only fakes on each side; a live probe against a real Claude Code session (confirming the Agent tool's actual `PreToolUse` shape and that Claude Code honors the deny response) remains separate, opt-in live evidence, unverified until run.

This rule ships enabled by default, matching the WD-014 decision text ("adding a new deterministic policy rule is a config/implementation change" -- deploying this code is what enables it, the same pattern already used for the `log` half). It also has a real, granular kill switch: `Limits.policy_intervene_same_model_subagent_spawn` (default `true`), the same `[defaults]`/`[projects.overrides]` mechanism `capture_content` already uses, so it is disableable globally or per project without pausing the daemon, and independently of any future second policy rule's own switch -- `_resolve_policy_decision` checks the resolved project's flag before ever touching the database. It never gates the rule's own `log` half, which stays unconditional per WD-014. `daemon pause` (which also tears down the policy socket via the same `ExitStack`) still stops everything, including this rule, as a coarser fallback. Two further, accepted gaps beyond the explicit-model-override recall gap already noted: a spawn during a session's very first coordinator response has no coordinator usage row yet (transcript enrichment runs on the daemon's poll cadence, and the `claude-transcript-v1` reader holds a response open until its closing `stop_reason` before emitting it), so it is allowed, not evaluated; and this always-on behavior has not yet been applied to this project's own user-local live instance (`LIVE.md`) pending explicit sign-off, since it changes real tool-call outcomes and its live probe is still unverified.
